# Commander

A personal command center that runs entirely on your own machine. It brings Linear, email, calendar, GitHub, daily notes, and to-dos into one place, with a local AI Agent that sorts incoming work and surfaces what needs attention.

Status: building v1. The spec is the completed wayfinder map in this repo's issues (label `wayfinder:map`); work is tracked in milestones M0–M8. Domain language lives in [CONTEXT.md](./CONTEXT.md).

## Running Commander (development)

Requirements: Node 24+ and pnpm 12+. On Linux, a Secret Service keyring (e.g. gnome-keyring) for token storage.

```sh
pnpm install          # also downloads Electron's binary (allowed in pnpm-workspace.yaml)
pnpm dev              # starts Commander; on Linux it runs natively on Wayland
pnpm test             # unit tests (Vitest)
pnpm test:perf        # speed checks (search, email sanitiser), one file at a time; run on a quiet machine
                      # (COMMANDER_EMBEDDING_MODEL_DIR=<folder> adds the real embedding model's checks)
pnpm test:e2e         # builds the app and runs the end-to-end tests (Playwright)
pnpm lint             # Biome lint + format check
pnpm typecheck        # TypeScript across the workspace
```

Layout: `apps/desktop` (Electron main, preload, React renderer), `apps/core` (the Core: syncs Sources, holds the Items and runs the Agent, as an Electron `utilityProcess`), and `packages/{domain,ui,sources,models}`. The window and the core talk only through validated messages (`packages/domain`).

### Data and the Item store

The Core's Item store is the only writer to Commander's database: one SQLite file (WAL, through Drizzle on better-sqlite3) at `commander.db` in Electron's `userData` folder (`~/.config/@commander/desktop` on Linux). A snapshot is taken daily into `snapshots/` next to it, keeping the last 7. The window reads and changes Items only through the typed Item store channel (`window.commander.itemStore(...)`). Projects live in the same database, written by the Item store too (`apps/core/src/item-store/projects.ts`); they are not Items, so changes to them (create, rename, recolour, reorder, archive, merge) go to their own Project log (`project_changes`), which powers their undo. Filing an Item into a Project is an Item change, so it is in the activity log and can be undone; a merge refiles every Item of one Project into another with an activity entry each.

People live there too (`apps/core/src/item-store/people.ts`, #117). Items keep the people involved as handles (`linear:<id>`, `github:<login>`, `teams:<id>`, an email address); after every save from a Source, each handle the Source named goes to the Person who has the email address it came with (case-insensitively: a Linear user's email, a GitHub login's public or commit email, a Teams member's address), so `github:priya-p`, Linear's Priya Patel and `priya@acme.io` become one Person. A handle with no known address is a Person of its own until one links it, and names never match anyone (ADR 0005). A Person goes by the richest Source's name (Linear or Teams full name, then GitHub name, then login or address) unless the User renamed them. **Settings → People** lists everyone, searchable, with Merge (pick two and the name to keep), Split (move handles out to a new Person) and Rename; each change goes to the People log (`people_changes`) and has Undo. Merging or splitting pins the handles it places, so matching never undoes it. The User is a Person too, recognised from their Accounts (`ownHandles` in `packages/domain/src/people.ts`). Rows and panes show people through the window's resolver (`apps/desktop/src/renderer/people/`): the Person's name, with every handle on hover; the Linear assignee and GitHub author filters offer People, and `Ctrl+K` lists People as their own group. A Person's name in a detail pane, and their row in `Ctrl+K`, opens their page (#122, see **A Person's page** under GitHub).

- **Schema changes:** edit `apps/core/src/item-store/schema.ts`, run `pnpm --filter @commander/core db:generate`, and commit the generated SQL in `apps/core/drizzle/`. The Core applies pending migrations when it starts.
- **Native modules:** better-sqlite3 ships Node-API prebuilt binaries (Linux, macOS and Windows on x64 and arm64), and Node-API binaries load in both Node (Vitest) and Electron (the Core), so there is no rebuild step. `pnpm-workspace.yaml` therefore declines its node-gyp fallback build; on any other platform, set `better-sqlite3: true` there and have a C++ toolchain installed. Search by meaning adds two, both pinned and both arriving with `pnpm install` (no build step): **sqlite-vec 0.1.9** (MIT OR Apache-2.0), a loadable SQLite extension, not a Node addon, whose per-platform package (`sqlite-vec-linux-x64` and so on, for Linux, macOS and Windows) better-sqlite3 loads into the same connection in Node and Electron alike; and **onnxruntime-node 1.30.0** (MIT), Node-API with its CPU binaries in the package, so `pnpm-workspace.yaml` declines its install script, which only fetches optional CUDA files. Both stay outside the bundle (`electron.vite.config.ts`) and are dependencies of `apps/desktop` so the built Core finds them. Where sqlite-vec can't load, the same distance function runs in JavaScript instead (slower, same answers).
- **Search index:** global search keeps an SQLite FTS5 index in the same file (`search_words`, with `search_docs` beside it), written by the Item store in the same transaction as each change, so it is never behind. Deleted Items and tombstones are left out of it. Emails are indexed by sender, recipients, subject, attachment names and the first 20,000 characters of their text, with FTS5 rowids that rise with when each was sent, so newest-first email search reads the index in order. It is derived data owned by the search module (`apps/core/src/search/`), not part of the Drizzle schema: it is built from the Items when missing (or when the module's index version changes), which takes about 4 s for 50,000 Items.
- **Search by meaning** (#73, ADR 0007): each indexed Item's searchable text, and each memory's text and keywords, has an embedding in `search_vectors` and `memory_vectors` (384 float32s in a BLOB, with the model that made it and a fingerprint of the text). They are derived data like the word index, outside the Drizzle schema, written by the Item store when the Core's meaning side (`apps/core/src/meaning/`) saves the embeddings it made in the background; a change to an Item's words marks its embedding out of date (the old one still finds it until the new one is in), and tombstones and deleted memories leave at once. The embedding model's files are downloaded once into `models/granite-embedding-97m-multilingual-r2/` next to `commander.db`.
- **Memory** (#74): Ares's memories are in `memories`, with their sources in `memory_sources`, written only through the Item store (`apps/core/src/memory/`); not Items, so not in the activity log. Their FTS5 word index (`memory_words`) and handle index (`memory_handles`) are derived data like search's, kept current in the same transaction as each save and rebuilt from the memories when missing.
- **Email bodies:** an email's detail (headers, snippet, labels, attachment names) is an ordinary Item detail; its bodies sit beside it in `email_bodies`, never in the detail or the activity log, so lists never load them: the text part (or, for an HTML-only message, its text conversion), cut at 200,000 characters, and the HTML as it came (never rendered as it is: the reader sanitises it first, see Reading email), left out when over 1,000,000 characters. Raw MIME isn't kept, and attachments are never downloaded during sync: the reader fetches a part (an inline image or an attachment) when it is first shown, saved or opened, and caches it in `email-parts/<Account>/` next to `commander.db`, readable by you only. A tombstoned email's bodies are deleted, as are an Account's, its cached parts and its image rules (`email_image_settings`, `email_image_trust`) when it is removed.
- **Throwaway data:** pass `--user-data-dir=<folder>` to Electron to run against other data. The end-to-end tests launch every app with a fresh temporary folder, so they never touch your real database.

### Build config (app client IDs)

The repo is public, so Commander's app registrations never go in it. They come from a private, git-ignored `config/local.json`, read at build time (`pnpm dev`, `pnpm build`, `pnpm test:e2e`) and injected into the main process. Without it, the committed `config/example.json` is used, which has no client IDs. A malformed file fails the build with the reason.

```sh
cp config/example.json config/local.json   # then fill in the client IDs
```

```json
{
  "linear": {
    "clientId": "your Linear OAuth app's client ID",
    "redirectPort": 48613
  },
  "microsoft": {
    "clientId": "Commander's Entra app: its Application (client) ID",
    "tenantId": "that app's Directory (tenant) ID"
  },
  "github": {
    "clientId": "Commander's GitHub App: its Client ID",
    "appSlug": "the app's slug, from github.com/apps/<slug>"
  },
  "google": {
    "clientId": "Commander's Google Desktop app OAuth client: its client ID",
    "clientSecret": "that client's client secret"
  }
}
```

The `microsoft` and `google` blocks are optional: without them (or with `null`s), Teams and Outlook, or Google, can't be connected. The `github` block is optional too: without a client ID, GitHub connects only with a token or gh's sign-in. Restart `pnpm dev` after changing the file.

### Accounts

**Settings → Accounts** (`,`) lists the Accounts of every Source, grouped by Source, each with its own **Connect**. Every Account can show **Reconnect** (when its sign-in failed for good) and be **Removed**. However a Source signs in, its tokens and API keys are stored only in the system keyring, through the secrets module; the window never receives one. The Accounts themselves (their names, how they signed in, and whether they need reconnecting) are kept in `accounts.json` in the `userData` folder. Each Source plugs into the same Account code (`apps/desktop/src/main/accounts/source-accounts.ts`) with its own sign-in, refresh and naming.

An Account can carry more than one Source that share its sign-in: a Google Account carries **Gmail** and **Google Calendar**, and an Outlook Account **Outlook** (mail) and **Outlook Calendar**, each with its own switch in Settings → Accounts. The sync engine keeps one queue per Account, so two Sources of one Account never call out at the same time, but each Source has its own cursor, cadence, status and back-off (kept per Account and Source in `commander.db`). Linear, Teams and GitHub Accounts carry one Source each and work as before.

### Connecting Linear

**Settings → Accounts** lists Linear Accounts by workspace name. Each Linear workspace is its own Account, and you can connect several. Connecting the same workspace again updates its Account rather than adding a second.

- **Connect Linear** signs in through your browser: OAuth with PKCE (S256) and no client secret, asking for `read` and `write`. Commander listens on `http://localhost:<redirectPort>/callback` only while a sign-in is open. It is offered only when `config/local.json` has a Linear client ID.
- **Use an API key instead** takes a Linear personal API key (Linear → Settings → Security & access → Personal API keys). It works without any OAuth app.
- Tokens and API keys are stored only in the system keyring, through the secrets module. If no real keyring is available, Commander refuses to connect and says how to fix it. The window never receives a token. The Accounts themselves (workspace name, how they signed in, and whether they need reconnecting) are kept in `accounts.json` in the `userData` folder.
- Access tokens last 24 hours. The main process refreshes one when it is within 10 minutes of expiry, the first time the Core asks for it. If Linear refuses a refresh for good (the access was revoked, or a refresh was replayed too late), the Account shows **Reconnect**. Reconnecting signs in again and keeps the same Account.
- **Remove** deletes the Account's keyring entry and its Items. Your notes and Todos stay, and their Links to removed Items show them as gone.

**Registering Commander's Linear OAuth app (once, by the owner):** in Linear, open Settings → API → OAuth applications → New. Name it "Commander", set the callback URL to `http://localhost:48613/callback` (use your `redirectPort` if you changed it; Linear matches it exactly, port included), leave webhooks off, and create it. Copy the **client ID** into `config/local.json`. Commander doesn't need the client secret, so never copy it anywhere. Then run `pnpm dev`, choose **Connect Linear**, and approve. This also confirms that Linear accepts the fixed loopback port.

The end-to-end tests never contact Linear: they point sign-in and sync at a fake Linear on this machine through `COMMANDER_TEST_LINEAR`, which only accepts loopback URLs.

### Connecting Teams

**Connect Teams** in Settings → Accounts signs in to Microsoft Teams with your work account, through Commander's own Entra app. Each Microsoft account is its own Account, shown as "Teams · <your sign-in>"; connecting the same account again updates it. Its Chats then sync (see **Teams Chats** under Syncing).

- Sign-in is OAuth 2.0 with PKCE (S256) and no client secret, against your organisation's single-tenant authority (`https://login.microsoftonline.com/<tenantId>/oauth2/v2.0/`). Commander listens on `http://localhost:<a free port>` only while a sign-in is open (Microsoft ignores the port of a registered `http://localhost`).
- It asks for `openid profile offline_access User.Read Chat.ReadWrite ChatMessage.Send Team.ReadBasic.All Channel.ReadBasic.All`: your Chats, sending messages, and team and channel names. None of these needs an administrator. Reading channel posts does, and is asked for separately (see **Channel posts** below).
- **Connect Teams** is offered only when `config/local.json` has both `microsoft.clientId` and `microsoft.tenantId`; otherwise it is shown disabled.
- If your organisation requires an administrator to approve apps (Microsoft's `AADSTS90094` or `AADSTS65001`), Commander says so, lists the permissions to approve, and offers your organisation's admin consent link to copy and send to your administrator.
- Access tokens last about an hour. The main process refreshes one when it is within 10 minutes of expiry, saving the new refresh token Microsoft issues before using the new access token. If Microsoft refuses a refresh for good (`invalid_grant`: revoked, expired or the password changed), the Account shows **Reconnect**; reconnecting signs in again as the same user and keeps the same Account.
- **Remove** deletes the Account's keyring entry and its Items.

**Setting up Commander's Entra app (once, by the owner):** use the app registration kept from the Microsoft sign-in test (rename it "Commander" if you like). In the Microsoft Entra admin center → App registrations → that app:

1. **Authentication:** under the **Mobile and desktop applications** platform (not Web, not Single-page application), make sure the redirect URI `http://localhost` is listed, exactly that, with no port or path. Add the platform and the URI if not. Leave **Allow public client flows** on if it is shown. Don't create a client secret: Commander doesn't use one.
2. **API permissions:** add **delegated** Microsoft Graph permissions `openid`, `profile`, `offline_access`, `User.Read`, `Chat.ReadWrite`, `ChatMessage.Send`, `Team.ReadBasic.All` and `Channel.ReadBasic.All`. None needs admin consent.
3. From the app's **Overview**, copy the **Application (client) ID** and **Directory (tenant) ID** into `config/local.json` under `microsoft` (see Build config above). Keep them out of the repo, issues, PRs and logs.
4. Run `pnpm dev`, choose **Connect Teams**, and approve in your browser.

The end-to-end tests never contact Microsoft: they point sign-in and Graph at a fake Microsoft identity platform and Graph on this machine through `COMMANDER_TEST_MICROSOFT`, which only accepts loopback URLs.

### Channel posts

Posts and their replies in the channels of your teams (#111) need one more delegated permission, `ChannelMessage.Read.All`, which only an administrator can approve for your organisation (Global Administrator, Privileged Role Administrator or Cloud Application Administrator). Replying in channels needs `ChannelMessage.Send`, which doesn't. Until a Teams Account's sign-in carries `ChannelMessage.Read.All`, nothing about channels shows anywhere except **Settings → Teams → Channel posts**, which says what's needed, names the permissions, shows these steps and the admin consent link to copy, and offers **Request access**.

**Approving Channel posts (once, by an administrator; the owner as CTO can):**

1. In the Microsoft Entra admin center → App registrations → Commander → **API permissions** → **Add a permission** → **Microsoft Graph** → **Delegated permissions**: add `ChannelMessage.Read.All` and `ChannelMessage.Send`.
2. Choose **Grant admin consent for** your organisation, and confirm. (Without the role, send the admin consent link Settings → Teams shows to someone who has it.)
3. In Commander, choose **Request access** in Settings → Teams → Channel posts and approve in your browser. This signs in to the same Account again asking for the two permissions too (incremental consent); your Chats keep syncing as before.
4. Switch on **Sync Channel posts**. Your teams and channels list under it; every channel syncs unless you **Exclude** it (or its whole team).

- Commander reads what the sign-in was granted from Microsoft's token response: without `ChannelMessage.Read.All` (the administrator hasn't approved it yet), Request access says so and shows the admin consent link, and Channel posts stay off. If the tenant refuses the sign-in outright (`AADSTS65001`, `AADSTS90094`), the same.
- If Microsoft later refuses to share channel messages for want of the permission (consent withdrawn), Channel posts go back to off with Request access, and the posts Commander held go. Refreshing the sign-in asks for the Channel post permissions too while they are granted, and falls back to the Chats' own if Microsoft no longer consents to them, so Chats never stop.
- Switching Sync Channel posts off, or excluding a team or channel, deletes the posts Commander holds from there (tombstones: Links show them as gone); switching on or including again brings them back with the next check.

### Connecting Outlook

**Connect Outlook** in Settings → Accounts signs in once for both Outlook Sources, **Outlook** (mail) and **Outlook Calendar**, through the same Entra app and sign-in as Teams (above). Each Microsoft account is its own Account, shown as "Outlook · <your sign-in>" and keyed by tenant and user, so connecting the same account again updates it. It is a separate Account from that user's Teams Account, with its own sign-in. Outlook mail and Outlook Calendar both sync (see **Outlook mail** and **Outlook Calendar** under Syncing).

- Sign-in, the `http://localhost` loopback, refreshing (rotated refresh token saved first, one refresh at a time), **Reconnect** and the admin consent explanation work exactly as for Teams.
- It asks for these permissions at once:

  | Permission | For |
  |---|---|
  | `openid`, `profile`, `offline_access`, `User.Read` | Who you are (the Account's name and key), and a refresh token |
  | `Mail.ReadWrite`, `Mail.Send` | Outlook: read, move, flag and delete mail, and send it |
  | `Calendars.ReadWrite` | Outlook Calendar: read and write events, including replies to invitations |

  `MailboxSettings.ReadWrite` is **not** asked for here: mirroring Buckets as Outlook categories (#142) asks for it separately, only when you switch mirroring on (Settings → Accounts → **Mirror Buckets to Outlook**, which signs in again for it: **Grant access**).
- Microsoft asks for every permission together, so both Sources are normally on. If the token covers only some (an administrator approved only part of them), the Source missing its permissions stays off with **Grant access**, which signs in again for that Account. You can switch either Source off and on.
- **Connect Outlook** is shown only when `config/local.json` has both `microsoft.clientId` and `microsoft.tenantId`; otherwise a line explains why.
- If Microsoft refuses a refresh for good, the Account shows **Reconnect** and both its Sources pause; reconnecting signs in again as the same user and keeps the same Account.
- **Remove** deletes the Account's keyring entry and its Outlook mail and Outlook Calendar Items.
- A personal Outlook.com account can't sign in to the single-tenant app; that waits for a multi-tenant registration.

**Adding Outlook to Commander's Entra app (once, by the owner):** in the Microsoft Entra admin center → App registrations → the Commander app set up for Teams → **API permissions**, add the **delegated** Microsoft Graph permissions `Mail.ReadWrite`, `Mail.Send`, `Calendars.ReadWrite` and `MailboxSettings.ReadWrite` (the last is only requested once Bucket mirroring is switched on). The redirect URI and the IDs in `config/local.json` are already in place from Teams. Then run `pnpm dev`, choose **Connect Outlook**, approve in your browser, and check that the Account appears with both Sources on. If your tenant asks for an administrator's approval, the error code is what to note (no tenant details).

The end-to-end tests use the same fake Microsoft identity platform and Graph as Teams (`COMMANDER_TEST_MICROSOFT`).

### Connecting GitHub

**Settings → Accounts** lists GitHub Accounts by login. Each GitHub user is its own Account, keyed by their GitHub user id, so connecting the same user again updates it. Its watched repos then sync (see **GitHub** under Syncing).

- **Connect GitHub** signs in to Commander's GitHub App with GitHub's device flow: Commander shows a short code with **Copy code** and **Open GitHub**; type it at github.com/login/device and approve. Commander checks with GitHub at the interval GitHub asks for (slower when GitHub says so) until you approve, decline, or the code runs out after 15 minutes. There is no loopback listener and no client secret. It is offered only when `config/local.json` has `github.clientId`.
- **Use a token instead** takes a **classic personal access token** with the `repo` and `read:org` scopes ([make one](https://github.com/settings/tokens/new?scopes=repo,read:org&description=Commander)). Commander only reads, though GitHub's `repo` scope also allows writing. Commander checks the token with `GET /user` and says which scopes are missing. Fine-grained tokens are turned away: each reaches only one account's or organisation's repositories, and GitHub doesn't say what one may read.
- **Use my gh sign-in** (shown when GitHub's `gh` command is installed) runs `gh auth token` once and stores what it prints, like a pasted token. If gh lacks a scope, Commander says to run `gh auth refresh --scopes read:org`.
- Tokens and gh's token are kept only in the system keyring, through the secrets module; the window never receives one (only the short code to type). Tokens and gh's token are never refreshed: if GitHub refuses one during a sync, the Account shows **Reconnect**, which asks for a token again.
- The GitHub App's user tokens last 8 hours, and its refresh tokens 6 months. The main process refreshes one within 10 minutes of expiry (with the client ID alone), saving the new refresh token before using the new access token, one refresh at a time. If GitHub refuses a refresh for good, the Account shows **Reconnect**; reconnecting signs in again as the same user.
- Under each app Account, Settings → Accounts shows where the app is installed ("Installed on sethtorrence, acme-org"), checked at sign-in, at each start and with **Check again**. Commander sees an org's private repositories only once the app is installed there. **Install on another org…** opens the app's install page, where org owners install it and members can request it.
- **Remove** deletes the Account's keyring entry and its Items.

**Registering Commander's GitHub App (once, by the owner):** on github.com, open your personal Settings → Developer settings → GitHub Apps → **New GitHub App**.

1. **GitHub App name** "Commander" (or a close variant if it's taken); **Homepage URL** this repo. Leave **Callback URL** empty and **Request user authorization (OAuth) during installation** unticked. Leave **Expire user authorization tokens** ticked. Tick **Enable Device Flow**.
2. **Webhook:** untick **Active**.
3. **Permissions → Repository permissions**, each **Read-only**: Actions, Checks, Commit statuses, Contents, Issues, Metadata (required) and Pull requests. Leave every **Organization** and **Account** permission at **No access**, so repository admins can install the app without an org owner.
4. **Where can this GitHub App be installed?** Any account. Create it.
5. From the app's settings page, copy the **Client ID** (it starts `Iv`) into `config/local.json` under `github.clientId`, and the slug from the app's public link (`https://github.com/apps/<slug>`) into `github.appSlug`. Don't generate a client secret or a private key: Commander needs neither. Keep the client ID out of the repo, issues, PRs and logs.
6. From the app's public page, **Install** it on your own account and on each org you oversee, choosing all repositories or just the ones you want.
7. Run `pnpm dev`, choose **Connect GitHub** in Settings → Accounts, and enter the code at github.com/login/device.

The tests never contact GitHub: they point sign-in and the API at a fake GitHub on this machine (device flow, REST and a sliver of GraphQL) through `COMMANDER_TEST_GITHUB`, which only accepts loopback URLs, and put a stand-in `gh` first on the `PATH`. The fake also answers what GitHub sync asks (the gates with ETags and free 304s, rate-limit headers, and the GraphQL below), and can refuse with a rate limit.

### Choosing what to watch (Settings → GitHub)

**Settings → GitHub** lists, for each GitHub Account, the orgs and repos it can reach, and which of them Commander watches. GitHub sync reads this list.

- **What's offered.** With the GitHub App: each installation's repos (`GET /user/installations` and each one's repositories), so only repos the install covers and you can access appear. Orgs you belong to without the app show as **Commander isn't installed here**, with **Install or request…** (the app's install page for that org, where owners install it and members can request it). With a classic token or gh's sign-in: your orgs (`GET /user/orgs`), your repos (`GET /user/repos`) and each org's repos. Archived repos never appear. **Add an org by name** covers an org GitHub didn't list.
- **The first time** (when you open Settings → GitHub, or at the Account's first sync, whichever comes first), Commander checks the repos you pushed to, opened pull requests in or reviewed in the last 90 days (one GraphQL query over your contributions). They show as ordinary checked repos.
- **Choosing.** Each org has **Watch whole org**, which also covers repos made there later; unchecking a repo inside it leaves just that one out. Other repos, and your **Personal repos**, have a checkbox each. A search box narrows the list, and a summary line says what is watched ("Watching 23 repos in 3 orgs."). Changes save at once.
- **Unwatching** a repo or an org that has Items in Commander asks first, saying how many Items go. Your notes and Todos stay, and their Links show those Items as gone.
- **Projects.** Beside each watched repo, the Project its own Rule ("repo is acme/titanlink-api", alone) files it into, and **Map to Project…**, which opens that Rule in the Rule editor, or a new one naming the repo with its Project for you to choose. It is a shortcut into the one Rules list (Settings → Rules), not a second way of filing.
- **Losing access.** A watched repo Commander can no longer reach (the app was uninstalled, your access ended, the repo was archived) stays watched and is listed under **Watched, but out of reach**, with **Unwatch**. Its Items stay until you unwatch it.
- **Where it's kept.** The Core lists what each Account can reach, with a token it borrows from the main process for each request. It keeps the choice through the Item store, in `commander.db` (`github_watch`): whole orgs (with any repos left out) and single repos, by node id. It keeps the rules rather than a list of repos, so new repos in a watched org are picked up. GitHub Items are keyed `<repo node id>:<…>` (`githubExternalId` in `packages/domain`), so unwatching a repo finds its Items.

### Connecting Google

**Connect Google** in Settings → Accounts signs in once for both Google Sources, **Gmail** and **Google Calendar**. Each Google account is its own Account, shown as "Google · <address>" and keyed by Google's account ID (the ID token's `sub`), so connecting the same account again updates it, and you can connect several. Gmail and Google Calendar both sync (see **Gmail** and **Google Calendar** under Syncing).

- Sign-in is OAuth 2.0 with PKCE (S256) in your browser, through Commander's Google "Desktop app" OAuth client. Commander listens on `http://127.0.0.1:<a free port>` only while a sign-in is open (Google accepts any port for desktop clients), checks the `state` it sent, and asks for `access_type=offline` and `prompt=consent` so Google always returns a refresh token, and `include_granted_scopes=true` so a later sign-in keeps what you already allowed.
- It asks for these permissions, and nothing broader (no IMAP, no `https://mail.google.com/`):

  | Permission | For |
  |---|---|
  | `openid`, `email`, `profile` | Who you are: the Account's ID, address and name |
  | `https://www.googleapis.com/auth/gmail.modify` | Gmail: read, label, archive, send and trash mail (never delete forever) |
  | `https://www.googleapis.com/auth/calendar.events` | Google Calendar: read and write events, including replies to invitations and events with guests |
  | `https://www.googleapis.com/auth/calendar.calendarlist.readonly` | Which calendars you have |
  | `https://www.googleapis.com/auth/calendar.app.created` | The "Commander" calendar for focus blocks |
  | `https://www.googleapis.com/auth/calendar.freebusy` | Colleagues' free/busy when finding time |

  `gmail.modify` is a restricted scope; the Calendar ones are sensitive or non-sensitive. That's fine unverified for personal use (under 100 users); verification is for paying Users later.
- Google lets you untick permissions on its consent screen. A Source missing any of its permissions stays off, with **Grant access** beside it, which signs in again for that Account; the Account works for whatever you allowed. You can also switch a granted Source off and on.
- If a Google Workspace admin hasn't allowed Commander (`admin_policy_enforced` or `org_internal`), Commander says so plainly rather than showing a generic error. Google may show that on its own page in your browser instead; then cancel the sign-in in Commander.
- **Connect Google** is shown only when `config/local.json` has `google.clientId`; otherwise a line explains why. The client secret is sent with the code exchange and each refresh: Google says a desktop client's secret isn't treated as a secret, but it still lives only in `config/local.json`, never in the repo.
- Access tokens last about an hour. The main process refreshes one when it is within 10 minutes of expiry, one refresh at a time per Account (Google keeps the same refresh token). If Google refuses a refresh for good (`invalid_grant`: revoked, expired, or the password changed), the Account shows **Reconnect** and its syncing pauses.
- **Remove** deletes the Account's keyring entry and its Gmail and Google Calendar Items.

**Setting up Commander's Google client (once, by the owner):** in the Google Cloud console, in the "Commander" project on your personal Google account:

1. **APIs & Services → Library:** enable the **Gmail API** and the **Google Calendar API**.
2. **Google Auth Platform → Audience:** user type **External**. Then **Data access → Add or remove scopes:** add the eight permissions in the table above. Back in **Audience**, choose **Publish app** so its status is **In production**, and leave it unverified: the "Google hasn't verified this app" warning is expected for personal use. In **Testing**, sign-ins expire after 7 days. No test users are needed once it is in production.
3. **Clients:** use the existing **Desktop app** OAuth client (no redirect URI to register: desktop clients accept any loopback port). From the client JSON you downloaded (keep it outside the repo), copy `installed.client_id` into `google.clientId` and `installed.client_secret` into `google.clientSecret` in `config/local.json` (see Build config above). Keep them out of the repo, issues, PRs and logs.
4. Run `pnpm dev`, choose **Connect Google**, accept the unverified-app warning (Advanced → Go to Commander), allow both Gmail and Calendar, and check that the Account appears with both Sources on.

The end-to-end tests never contact Google: they point sign-in, the Calendar API and the Gmail API at a fake Google on this machine through `COMMANDER_TEST_GOOGLE`, which only accepts loopback URLs (without a `calendarUrl` or `gmailUrl`, each is the fake's own).

### Syncing

The Core's sync engine keeps each Account current. A newly connected Linear Account syncs at once: every issue you can see that is open, plus those completed or cancelled in the last 30 days, arrive as `linear-issue` Items. After that Commander asks Linear only for what changed (issues and comments updated since the last sync), every **15 minutes** by default; each Account can be set to 30 or 60 in Settings → Accounts, which also shows its last sync, how many issues it holds, the next sync, any problem in plain words, and **Sync now**.

- Each Account syncs on its own, so a slow or failing one never holds up another. Syncing pauses while the machine sleeps or is offline and catches up once afterwards.
- After a failure Commander waits 1, 2, 4… minutes (at most an hour) before trying again, and always waits as long as Linear's rate limit asks.
- Issues archived or deleted in Linear stay in Commander as tombstones, so Links to them survive. Your filing, Links and notes are never touched by a sync.
- If Linear refuses an Account's sign-in (an API key revoked in Linear, say), the Account shows **Reconnect** and only its syncing pauses.
- Where each Account's sync stands (its cursor, last sync and back-off, never a token) is kept in `commander.db`, with a short history of sync runs and the query complexity Linear reported for each.
- Each sync also fetches what the detail pane's pickers offer (each team's workflow states, members, labels, cycles not yet over and Linear projects), kept per Account in `commander.db`.

**Teams Chats.** Every Teams Chat you are in (one-to-one, group and meeting) is a `chat` Item: its title is the Chat's topic, or the other people's names; its People are everyone in it (`teams:<user id>` and their email address); and it keeps its recent messages as plain text converted from Teams' HTML (paragraphs, lists, links and @mentions kept; scripts, styles and markup dropped; inline images shown as "[image]"; files as links, never downloaded), with reactions, mentions, replies, your last read time, and what's unread and whether it mentions you. Microsoft Graph has no change feed or push for a desktop app, and Microsoft asks apps to check Teams about once a day, so:

- A newly connected Teams Account syncs at once: every Chat, plus the last 30 days of messages (the newest 200 per Chat) from Chats active in that time. Older history is not fetched.
- A **full sync** runs once a day, and also re-reads the last 7 days of Chats active in them, catching edits, deletions and reactions the check can miss.
- A **check** runs on **Sync now**, and (unless you switch off **Also check whenever another Source syncs** in Settings → Accounts) a moment after any other Source's Account finishes syncing, never more than once every 5 minutes. It makes one request for the Chat list (`/me/chats?$expand=lastMessagePreview`) and fetches messages only from Chats that changed, filtered on `lastModifiedDateTime`. In practice Teams stays as fresh as Linear, at the risk Microsoft warns of: checking more often than daily may slow or pause Teams access for Commander.
- Commander sends at most one request a second per Chat. When Microsoft asks it to slow down (429, or 503 with Retry-After), it stops at once and waits at least as long as asked, checks included.
- The activity log keeps a Teams sync's change to a Chat compactly: how many messages were added, changed or removed and the newest, not copies of them (the domain's `logged-fields.ts` lists detail fields kept this way; changes made in Commander are always logged whole). Such entries can't be undone.
- Chats you leave, or that are deleted, stay in Commander as tombstones. Settings → Accounts shows the last check, the next full sync, the switch and **Sync now**. `Ctrl+K` finds a Chat by its title or by what was said in its recent messages, and opens it in the Teams Section. Chats you exclude in the Teams Section are skipped by every sync (nothing is fetched for them) until you include them again.
- Rules can file Chats by **Account**, **Chat** (by its Teams id, labelled with its name), **person in Chat** (by email address, or Teams user id for someone without one; never you), **Chat type** (one-to-one, group, meeting) and **Chat name contains** (`teams.*`): "person in Chat is Omar Haddad → TL" or "Chat is TL eng → TL" files Chats as they sync ("Filed under TL by Rule: …"), and the Rule editor offers the values your synced Chats have, with the live count, sample and re-filing preview. Channel posts add **team** and **channel** (`teams.team`, `teams.channel`): "team is Titanlink → TL" files every post in that team.

**Channel posts.** With Channel posts approved and switched on (see **Channel posts** under Connecting Teams), each post in a channel you sync, with its replies, is a `channel-post` Item: its team and channel, subject (its title, or else the post's first line), the post and its replies as plain text converted exactly as Chats' (scripts, styles, frames and markup dropped, images as "[image]", files as links), mentions of people and of whole teams or channels, reactions and its Teams link. Microsoft Graph has no change feed for channels any more and listing a channel's messages takes no filter, so Commander polls, gently, after the Chats (which are saved first, so channel polling never holds them up):

- Teams and channels are listed (`/me/joinedTeams`, `/teams/{id}/channels`) on the first channel sync and on each daily full sync.
- Per channel, one request (`/teams/{t}/channels/{c}/messages?$top=20&$expand=replies`): Graph lists threads by their latest change, post or reply, so Commander stops at the first thread it has already seen and a quiet channel costs one request. More replies than a thread's expansion holds are paged. The first sync reads threads active in the last 14 days (the newest 100 per channel).
- Bounded per sync: the daily full sync reads every channel (up to 200, at most 600 requests); each light check (Sync now, opening the Section, after other Sources) at most 15 channels that are due (one active in the last week every 10 minutes, a quiet one every 6 hours, a new one at once), oldest checked first, at most 45 requests. Each channel gets at most one request a second (Teams' limit) and channel requests are spaced 200 ms apart; a 429 or 503 with Retry-After stops the sync at once, keeping what it did, and the next waits as long as Microsoft asked.
- A deleted post becomes a tombstone; a deleted reply stays, marked deleted. Teams keeps no read state for channels, so Commander keeps its own **seen** mark per post (opening it marks it seen; never sent to Teams).

**Google Calendar.** Every event on the calendars you have on, in every connected Google Account, is an `event` Item: its title, its calendar (name and colour), start and end with their time zone (or its days, for an all-day event), location, description (plain text converted from Google's HTML, like Teams messages), organiser, guests and their answers, your own answer, the meeting link, busy or free, private or not, the recurring series it belongs to, and its Google Calendar link. Its People are the organiser's and guests' addresses. Push needs a public webhook, so Commander polls (decisions #2, #17):

- Each sync lists the Account's calendars (`calendarList`). Settings → Accounts shows them under Google Calendar, each with a switch: the primary calendar and those you own start on, subscribed ones (holidays, a colleague's) off. Switching one off stops syncing it and hides its events at once (they stay as tombstones, filed and linked as they were); switching it back on syncs it.
- A calendar is first read in full with `events.list?singleEvents=true`, so recurring events arrive as their instances, each its own event naming its series, from **30 days back to 12 months ahead**. Google's sync guide restricts the first read with `timeMin`/`timeMax` and still issues a `syncToken` on its last page; later reads send only that token (Google refuses the window alongside it) and get every change wherever it falls, so new events outside the window are dropped when saving, while events Commander already holds are kept current.
- After that, every **15 minutes** by default (30 or 60 in Settings → Accounts), Commander asks only for what changed since each calendar's sync token. Cancelled events, and every instance of a cancelled series, become tombstones. A `410 Gone` (the token expired) makes the engine read the Account's calendars again from scratch, and events no longer there become tombstones. Google's quota answers (403 `rateLimitExceeded` / `userRateLimitExceeded`, and 429) back off like any rate limit.
- Rules can file events by **calendar**, **organiser**, **attendee**, **title contains** and **Account**: "calendar is Titanlink Standups → TL" files events as they arrive. `Ctrl+K` finds events by title, location, guests and description, in their own Calendar group.

**Outlook Calendar.** Every event on the calendars you have on, in every connected Outlook Account, is the same kind of `event` Item, through Microsoft Graph v1.0 over `fetch` (decisions #3, #17, #20): busy or free from `showAs` (free and working elsewhere leave the time open), private from `sensitivity`, the Teams or other online-meeting link, your own answer from `responseStatus`, the Outlook on the web link, and the time zone Outlook names the Windows way ("Pacific Standard Time") as its IANA name. Change notifications need a public endpoint, so Commander polls with delta queries:

- Each sync lists the Account's calendars (`/me/calendars`). Settings → Accounts shows them under Outlook Calendar, each with a switch: the default calendar and those you own start on; shared, holiday and birthday calendars (ones you can't edit, or someone else owns) off.
- Each calendar on is read with `/me/calendars/{id}/calendarView/delta` (recurring events arrive as their instances, each naming its series) over the same **30 days back to 12 months ahead**, then from the delta link Graph hands back, kept per calendar. Every request sends `Prefer: IdType="ImmutableId"` and a page size, so an event moved to another calendar keeps its Item, filing and Links.
- A delta's window is fixed when it starts, so once its start is more than 7 days old the calendar starts a fresh delta: a quiet full re-read that saves only what changed and tombstones events in the new window it no longer returns (older ones are left alone).
- Every **15 minutes** by default (30 or 60 in Settings → Accounts). Deleted (`@removed`) and cancelled events become tombstones, and removing a series takes every instance. An expired delta link (410, `SyncStateNotFound`, `resyncRequired`) makes the engine read the Account's calendars again from scratch. 429s, and 503s with `Retry-After`, back off for at least as long as Microsoft asks, and no more than 4 requests run at once per mailbox (calendars are read side by side).
- The calendar Rule fields read Google's and Outlook's events alike (`google-calendar.*` and `outlook-calendar.*` are both registered; the Rule editor offers them once, under Calendar), so "organiser is Dana Ruiz → TL" files both Accounts' events.

**GitHub.** Pull requests, issues, review requests and releases from the repos an Account watches (Settings → GitHub) arrive as `pull-request`, `github-issue`, `review-request` and `github-release` Items, every **15 minutes** (the only choice). GitHub can't push to a desktop app, so Commander polls, as cheaply as GitHub allows (`packages/sources/src/github/`):

- **Open work, every sync:** one light GraphQL request with four searches (`is:open is:pr author:@me`, `is:open is:pr user-review-requested:@me`, `is:open is:pr team-review-requested:@me`, `is:open is:issue assignee:@me`) listing ids and update times only (about a point); those new or changed are then fetched whole. Each review asked of you on an open pull request, directly or through one of your teams, is a `review-request` Item naming the pull request's Item; once the review is given or the request withdrawn it becomes a tombstone, at the end of the sync, after the searches below have saved the pull request as it is now (so its Todo can say whether the review was given). Open work outside the watched repos is left out.
- **Gates, per watched org:** `GET /orgs/{org}/repos?sort=pushed` and `GET /orgs/{org}/issues?filter=all&state=all&sort=updated` with `If-None-Match` and the ETags from last time; for personal repos, `GET /user/repos?sort=pushed&affiliation=owner,collaborator` and each watched repo's issues. A `304` costs nothing, and all `304`s end that org's sync there.
- **When a gate changed:** a GraphQL search (type pinned to `ISSUE_ADVANCED`) over the org's pull requests and issues updated since last time, split into narrower time windows while one would pass GitHub's 1,000 results, keeping only watched repos; then batched GraphQL over the repos pushed to since (25 per query, halved when GitHub times out or answers 502) for the default branch's head commit and checks, its commits since, and releases.
- **First sync** (of each org, and again when more of its repos are watched): open pull requests and issues, those closed or merged in the last 30 days, and releases from the last 30 days.
- **What's kept:** a pull request's repo, number, author, state (open, closed, merged), draft, branches, labels, assignees, requested reviewers (people and teams, with when they were asked), the latest review per reviewer and the review decision, the head commit's check state, the issues it closes, its size, its body (read-only Markdown) and its times; an issue's repo, number, author, assignees, labels, milestone, state and why, body, comment count, times, and its parent and sub-issue counts; a release's tag, name, author, time and notes. People are `github:<login>`, plus email addresses GitHub ties to those logins (a public profile email, the head commit's author), never GitHub's no-reply addresses.
- **Rules** (#118) can file pull requests, issues and releases by **Account**, **org**, **repo** (by node id, reading `owner/name`), **label**, **author**, **milestone**, **kind** and **title contains**: "repo is acme/titanlink-api → TL" files every pull request, issue and release from it as it arrives ("Filed under TL by Rule: repo is acme/titanlink-api"), and that is how the oversight summary groups work by Project. The Rule editor offers the values of synced Items and every watched repo (so a repo with nothing synced yet can be chosen). A review request isn't filed by Rules: it takes its pull request's Project (filed as inherited) and follows it, as its Todo does.
- **Repo health** (not Items), per watched repo in the Account's catalog in `commander.db`: the default branch, its head commit's check state (looked at again each sync while checks are still running) and the last week's commits, reverts flagged.
- **Gone:** once a day the open pull requests and issues held are looked up by id; one GitHub deleted, or that moved to another repo, becomes a tombstone. A watched org or repo GitHub won't show any more is skipped, and its Items stay until you unwatch it.
- **Limits:** GitHub allows 5,000 REST requests and 5,000 GraphQL points an hour, shared with your other tools. Every sync records the REST requests GitHub counted and the GraphQL points it charged, and Settings → Accounts shows the last hour's use ("Last hour: 12 of 5,000 REST requests · 41 of 5,000 GraphQL points"). Commander leaves 500 of each for your other tools: with less left it stops and waits for the reset. One sync spends at most about 400 points, leaving the rest of the orgs to the next. When GitHub says to slow down (403 or 429, its hourly or secondary limits) Commander waits at least as long as `Retry-After` asks, or until the reset (a minute when GitHub says neither).
- `Ctrl+K` finds a pull request or issue by `owner/repo#123` (or `repo#123`) and by the words of its body.
- **Oversight summary** (#119), at the top of the GitHub Section in a collapsible panel: for **Since yesterday** (the default), **This week** or **Custom since…** a day, over everything or one Project, what **Shipped** (pull requests merged and issues closed as done, per repo, with releases), what **Started** (pull requests and issues opened, leaving out `[bot]` logins, the bots listed in Settings → GitHub, and drafts opened and closed in the range), what's **Stuck** (open, non-draft pull requests with a review asked more than 2 days ago and none since, with failing checks, or older than 7 days with no activity for 5; both numbers in Settings → GitHub) and what's **On fire** (a watched repo's default-branch head failing its checks, revert commits on a default branch), grouped by Project (Items' filing; a repo's fire goes where most of its Items are, Unfiled last) then repo, ending "Nothing on fire" when that's true. It is made in the Core from the Items and repo health Commander holds, with no model and no request to GitHub (`oversightSummary` in `packages/domain/src/github-oversight.ts`, the facts Ares writes from; reviewers show as their People). Each line opens its Items in the Section: one opens its detail, several are listed on their own, a fire filters to its repo. When Ares has written the summary for what the pickers show today (see **Write the GitHub summary** under Ares's jobs), his replaces these plain lines, and when he can't, the plain lines say why.
- **People** (#122), the GitHub Section's fourth view beside Your work, Pull requests and Issues: one card per Person active in the watched repos (they authored, merged or reviewed a pull request in the range, have one open, or a review is waiting on them; the User, who has Your work, and bots are left out), **always by name**, never by their numbers: nothing ranks, scores or compares People. **This week** (the default, from Monday) or **Last 7 days**; the Section's Project filter narrows each card to that Project's work and drops People with none there. Each card shows **Merged** and **Reviewed** (counts that expand to their pull requests), their **open pull requests** with how long each has been open and why it is Stuck by the summary's rules, the **reviews waiting on them**, oldest first, with how long each has waited, and their open **Linear issues** with state (through the Person's Linear handle), with plain marks for what is worth a look ("3 reviews waiting, oldest 4 days", "PR open 12 days", "1 PR stuck"). Below, Ares's paragraph about their week (see **Write the GitHub summary**), with **Refresh**; with none yet, or the model off, the card shows its facts alone. Rows open their pull request here or their Linear issue in Linear; the name opens the Person's page (`githubPeople` in `packages/domain/src/github-people.ts`, made in the Core from the Items held).
- **A Person's page** (#122): from a People card, `Ctrl+K` or a Person's name in a detail pane (a pull request's author and reviewers, a Linear issue's creator and commenters, a Chat message's sender), a temporary tab like a Project page: their card over the **Last 30 days** (or **90**), with Merged and Reviewed open, Ares's latest paragraph and Refresh, every handle they have by Source, and **Settings → People** to merge or split them. `Esc` goes back.
- **Skill-managed issues** (#120): wayfinder maps and build tickets kept open for weeks on purpose are recognised by label (Settings → GitHub → Skill-managed labels; by default `wayfinder:*` and the five triage labels, a trailing `*` matching any suffix; `wayfinder:map` is always a map). A map's tickets are its sub-issues, else issues whose body starts with `Part of #<map>`, else those in its task list; build tickets with no map group by milestone. The summary gets a **Progress** section: one line per map or milestone that moved in the range ("acme/api#1 Commander v1 map: 15 of 26 decided, 2 opened and 3 closed, 1 blocked"; closed as not planned counts as decided), with a thin bar. Tickets count under **Started** only once claimed (assigned) in the range, under **Shipped** once closed as done (a pull request that closed one shows once, with it: "#170 closes #66 (build ticket)"), and never as Stuck. In the Issues view they sit under their map or milestone, collapsed, with the same progress; the map's row shows its progress instead of its age. GitHub issues are never ranked on the Dashboard for themselves: a claimed ticket shows through its GitHub Todo. Commander holds closed issues from the last 30 days only, so the counts fill in older tickets from GitHub's own (the map's sub-issue summary, the ticks in its task list, the milestone's open and closed issues); sync keeps each issue's assignment time and its blockers (GitHub's issue dependencies) for this (`packages/domain/src/github-skill-issues.ts`).
- **Finishes Links:** after each GitHub sync (and after a Linear sync brings issues), a pull request whose title, branch or body names a Linear issue Commander holds (`ENG-412`, `priya/eng-412-…`, a Linear link, any of Linear's closing words; not after "Part of", "Related to", "Ref"…), or whose closing issue (GitHub's list, or `Closes #30` / `Fixes org/repo#45` in its body) names one or is linked to one, gets a **finishes** Link to it, made by GitHub and shown from both ends. **Remove** beside it in the pull request's detail takes it away for good: a Link once made is never made again.
- **The writer's detail:** after each GitHub sync, for the Account's pull requests in today's summary, Commander fetches what Ares will read (the description, closing issues' titles and bodies, reviews and review comments, the first 30 comments, and a change outline: files changed grouped by area such as `apps/core`, with additions and deletions, from the first 100 files; never the diff), 25 pull requests per GraphQL query, kept beside the pull request (`github_details.writer_detail`) until it changes.

**Gmail.** Every message in a Google Account with Gmail on is an `email` Item (one per message, ADR 0001): its title is the subject, its People are the addresses involved, and it is **open** while in the inbox and **archived** once not. Its detail keeps Message-ID, In-Reply-To and References, the thread, the Gmail thread id, from, to, cc, bcc, reply-to, the date, Gmail's snippet, read, starred, inbox, sent, Gmail's labels, attachment names, types, sizes, part ids and Content-IDs, whether it carries a calendar invitation, and its `List-Unsubscribe` and `List-Id`. Bodies are kept beside it (see Data and the Item store). Gmail has no push for a desktop app, so Commander polls:

- **First sync:** the 30 days before the Account was connected (Spam and Trash left out; drafts kept apart, see Writing email), newest first, each message fetched whole (`messages.get?format=full`), paced to about 250 a minute under Gmail's quota of 6,000 units a minute per user (`messages.get` costs 20), after a short burst so the newest mail shows within seconds while the rest backfills. Settings → Accounts and the Email Section show "Downloading 30 days: 1,240 of ~3,000". A first sync stopped by a restart or Gmail's quota carries on where it stopped, fetching only what Commander doesn't hold.
- **After that:** only what changed, from Gmail's history (`history.list`): new mail, deletions and label changes. Deleted messages, and messages moved to Spam, become tombstones; a message moved to Trash stays, in the Email Section's **Trash**; read, starred, archived and labels follow Gmail without fetching the message again. Every **15 minutes** by default; each Account can be set to 5, 10, 15, 30 or 60 in Settings → Accounts, and opening Email or pressing **Refresh** syncs at once.
- **Quota:** Gmail answers a spent quota with 403 `rateLimitExceeded` (or 429); Commander stops, says "Gmail asked Commander to slow down.", and waits at least a minute (longer if Gmail says so, and longer after each failure in a row).
- **Expired history** (Gmail keeps about a week): the same 30-day window is read again, fetching only messages Commander doesn't hold, refreshing the labels of the rest from one listing per label rather than a fetch per message, and tombstoning what Gmail no longer has. Your filing, Links and notes are never touched by a sync.
- **Threads** are built by Commander from the reply headers (Message-ID, In-Reply-To, References), whatever order mail arrives in; only a message with no reply headers falls back to Gmail's thread. Outlook's mail is threaded the same way.
- Each email's text goes through the same steering check as other outside Items, so one aimed at Ares gets the warning mark.
- **Organising** (#135): archive, read and unread, star, Trash and labels are edits of each message's synced fields, `inbox`, `read`, `starred`, `trash` and one `label:<id>` per label (ADR 0003), queued for Gmail like a Linear edit and written by the Gmail adapter: `messages.trash` / `untrash`, then one `messages.modify` for the rest. A thread's action is each of its messages' (Gmail stars only a conversation's latest message, and so does Commander). The adapter reads the message's labels first: what Gmail already has isn't sent, and a field Gmail changed since Commander last saw the message (its history since the historyId the Item carries) stays as Gmail has it, noted "Changed in Gmail at 14:02". Gmail's history has no times, so a change made in Gmail after Commander last synced the message counts as the newer one. Changes made offline wait in the queue; repeated failure, or a change Gmail refuses, shows **Couldn’t sync** with **Retry** on the thread. Nothing deletes for good: the `gmail.modify` scope can't, and Trash is as far as it goes. Each Account's labels are kept from its last sync (`source_catalogs`) for the label picker and the views.
- **Snooze** is Commander's own (Gmail's API has none): a snoozed thread's messages carry a `snooze` field that is edited, logged and undone like the others but never queued for Gmail, and a sync keeps it. The Core brings snoozed threads back when their time comes (`apps/core/src/snooze/`), looking at start-up too, so one whose time passed while Commander was closed comes back on the next start: back at the top of the inbox, the latest message marked unread (which does reach Gmail), with "Snoozed until 09:00" until it is archived. New mail in a snoozed thread brings it back at once, as in Gmail, and trashing or archiving it unsnoozes it. It needs Commander running, the window or the tray, to return mail on time, as the snooze picker says.
- **Buckets** (#137) say what to do with an email: every email sits in one Bucket or is **Unsorted**, whatever its Project. A fresh install has seven, each with a plain description written for Ares to sort by (#141): Needs reply, Waiting on others, FYI, Newsletters, Receipts, Calendar and Junk; **Settings → Buckets** renames, describes, adds, removes (its emails become Unsorted and its Rules go, with Undo) and reorders them (`buckets` in `commander.db`; the starter ids stay fixed, so Needs reply is still found once renamed). An email's Bucket is Commander's own field, `bucket` (`{ bucketId, sortedBy: rule | ares | user }`), edited, logged and undone like snooze and never sent to Gmail unless the Account mirrors its Buckets (below, off by default). A thread's Bucket is its latest message's, so new mail in a thread arrives Unsorted unless a Rule sorts it. The Email Section's **Bucket strip** (All, Needs reply, the rest in your order, Unsorted, each with its count under the views, the Account switcher and the Project filter) narrows the list, each row shows its Bucket, and `v` moves a thread (its number in the picker, `0` for Unsorted), recorded as yours. **Bucket Rules** sort email in the one list of Rules (the first match per kind of target wins, so a Project Rule and a Bucket Rule can both match an email) by the email fields Gmail and Outlook share (`gmail.*`, read from both: from address, from domain and its parents, to or cc, subject contains, Account, mailing list, has attachment, label or folder), which Project Rules can use too. Mail you sorted by hand is never touched, and Ares never moves mail you or a Rule sorted. Creating or changing a Bucket Rule offers "Also re-sort 42 existing emails?" with a preview; one Undo puts them back. Threads in Needs reply go to Today on the Dashboard ("Dana’s waiting on your reply since Tuesday") and those in Waiting on others with no answer for 3 days to Waiting on others ("No reply from Leo for 4 days"); the Email tab counts unread threads in Needs reply.

**Buckets in Gmail and Outlook** (#142), both off until you switch them on:

- **Skip the inbox**, per Bucket (Settings → Buckets; off for every starter Bucket, suggested for Newsletters, Receipts and Junk). Mail you sort into it is archived at once, in the same change (undo brings it back to the inbox). Mail a Rule or Ares sorts into it is offered for archiving as Tidy your Sources / "Skip the inbox" (Ask by default): a suggestion on the email (Archive or Not now) and, in the Bucket view, "Archive 8 Newsletters?" with **Accept all**; at Auto it is archived on arrival, as Ares, undoably. Switching it on offers the mail already in the Bucket, only ever as suggestions. A correction from Gmail or Outlook (below) never archives by itself.
- **Mirror Buckets**, per Account (Settings → Accounts, under the Account's Sources). Commander says what will happen first; for Outlook it then signs in again asking for `MailboxSettings.ReadWrite` (**Grant access**), which making categories needs. While on, each email shows its Bucket as exactly one `Commander/<Bucket>` label in Gmail (nested under a `Commander` label) or "Commander: <Bucket>" category in Outlook (in Outlook's preset colours, wrapping after 25), beside your own labels and categories, which are never changed. It is the `bucket-mirror` synced field, queued through the outgoing queue only for a mirroring Account; the labels themselves are made, renamed with their Bucket (Outlook categories can't be renamed: a new one is made and the old one deleted) and deleted with it by a label plan the sync engine carries out before the Account's writes (`bucket_mirror_labels`). Switching it on sets Tidy your Sources / "Mirror Buckets" to Auto in the Autonomy grid; lowering that below Auto pauses it. A Commander label or category you change in Gmail or Outlook moves the email to that Bucket in Commander, recorded as your sort (a correction for Ares). Switching it off stops writing at once and offers **Remove Commander labels** (or categories), which takes them off every email and deletes them, or **Keep them**.

**Outlook mail** (#136). Every message in an Outlook Account with Outlook (mail) on is the same kind of `email` Item as Gmail's, through Microsoft Graph v1.0 over `fetch` (decisions #3, #8, #15, #20), and behaves the same in the Email Section. Where Gmail has labels, Outlook has **folders**: a message is filed in one, open while that is the Inbox and archived anywhere else; its flag is its star; its categories are kept as Outlook has them but not offered as labels (Buckets will write back as categories, #16). Change notifications need a public endpoint, so Commander polls with delta queries per folder:

- Each sync lists the mailbox's folders (`/me/mailFolders`, with child folders, named by their path: "Inbox / Receipts") for Move to folder and the views; which are Outlook's own Inbox, Archive, Sent Items, Deleted Items and so on is asked once, in one JSON batch. Every folder is synced except Junk Email, Drafts, Outbox, Conversation History, Sync Issues and Deleted Items (and their child folders), each with its own delta link (`/me/mailFolders/{id}/messages/delta`), asking for immutable ids so a message moved between folders keeps its Item, filing and Links, and selecting `internetMessageHeaders`, so threading needs no request per message.
- **First sync:** the 30 days before the Account was connected (a `receivedDateTime ge` filter), the Inbox first and newest first, saved page by page; it is counted first for "Downloading 30 days: 120 of ~800", and a first sync stopped by a restart or a rate limit carries on from the page it reached. Attachments' metadata (inline images too) comes in batches of four; their bytes only when you open one.
- **After that:** only what changed in each folder. A message gone from one folder and found in another moved; one gone from every synced folder (deleted, or moved to Junk Email) becomes a tombstone. Deleted Items isn't downloaded, but a message Commander holds that goes there shows in **Trash**, remembering the folder it came from, until Outlook deletes it for good. Same cadence as Gmail: every 15 minutes by default, 5 to 60.
- **Threads** come from the reply headers, as Gmail's; only a message without them (the User's own sent mail, which Outlook leaves without internet headers) falls back to Graph's `conversationId`, so a reply in Sent Items joins its conversation.
- **Limits:** no more than 4 requests at once per mailbox, shared with the Account's Outlook Calendar (Outlook's limit); 429s, and 503s with `Retry-After`, wait as long as Microsoft asks. An expired delta link (410, `SyncStateNotFound`) reads that folder's 30 days again, tombstoning what it no longer lists.
- **Organising:** the synced fields `read` (`isRead`) and `starred` (the flag) go as one `PATCH`; where a message is filed as one `move`: `inbox` (archive moves it to Archive, and undo back to the Inbox), `trash` (Deleted Items, and back to the folder it came from) and `folder` (**Move to folder**, `l` on an Outlook thread, which opens a folder picker instead of labels; your own sent messages stay in Sent Items, as Outlook moves a conversation). The adapter reads the message first: what Outlook already has isn't sent, and a field changed in Outlook since Commander last synced it, later than your change (`lastModifiedDateTime`), stays as Outlook has it. Snooze stays Commander's own.

**Writing email** (#138). The Email Section writes mail for Gmail and Outlook alike: `c` new mail (a sheet of its own, from the default Account in **Settings → Email**, changeable per message), and on a thread `r` reply, `Shift+R` reply all and `f` forward (below the thread, from the Account the message arrived at). To, Cc and Bcc suggest addresses from your own mail (people you've written to first, then by how often and how recently seen); the body has bold, italic, links and lists (`Ctrl+B`, `Ctrl+I`, `Ctrl+K`), sent as HTML with a plain-text alternative; attachments come from **Attach** or a drop, each with its size, up to 35 MB together; a reply's quoted history sits folded below it, as text; each Account's signature (**Settings → Accounts**, stored in Commander) starts every message and can be edited in it. Nothing anyone else wrote is ever rendered in the window: the composer holds its own model (paragraphs and lists of plain, bold, italic and linked text), pasting inserts text only, and the quote goes into the message as the reader's sanitiser cleaned it.

- **Drafts:** after a pause in typing the message is saved, an `email` Item marked as a draft (never in a thread or a view), and its draft goes to the Account's **Drafts** folder through the outgoing queue (`drafts.create` / `update` in Gmail; in Outlook a draft made with `createReply` / `createReplyAll` / `createForward`, or `POST /me/messages` for new mail, then PATCHed), so it can be finished in Gmail or Outlook. Drafts made there sync in (Gmail's `drafts.list` when a sync meets a draft change; Outlook's Drafts folder by delta) and show in the **Drafts** view, opening in the composer. Sending or discarding removes the draft there too. Commander's record of each message (its body as the composer's model, its attachments, the quote and its Message-ID) is `email_compose`, beside the Item; attachments wait in `compose-files/` next to `commander.db`, readable by you only, until sent.
- **Undo send:** every send is held in the Core's outgoing queue for **10 seconds** by default (Settings → Email: 5, 10, 20, 30 or 60) with a "Sending… **Undo**" toast; the message shows in its thread at once, and Undo opens the composer again with everything in it. The hold runs in the Core, so closing the window to the tray keeps it, and quitting sends held messages first (within 15 seconds). Gmail's send is `messages.send` with raw MIME built by Nodemailer's MIME builder (into the thread's `threadId`, through the upload endpoint over 4 MB); Outlook's is the draft's `send`, attachments over 3 MB through an upload session.
- **Outbox:** a message offline waits in the **Outbox** view and goes on reconnect, and can be taken back until then; one the Source refuses stays there with its reason and **Retry**. Only you send: Ares can draft, never send.
- **Never twice:** every message carries Commander's id (an `X-Commander-Id` header in Gmail, an extended property in Outlook) and a Message-ID fixed when it is first saved. An attempt whose outcome is unknown (a timeout, a dropped connection, Commander quitting mid-way) is retried only after the adapter looks for what it did: in Gmail the sent mail since the attempt, in Outlook Sent Items and the Outbox (and a draft gone since counts as sent); if Gmail can't tell, nothing is sent and the Outbox says to check Sent. The Source's answer gives the message's Item its id, and a sync that gets there first is matched by Message-ID, so a sent message appears once in its thread.

### Two-way sync

Changes you make to a Linear issue in Commander (state, assignee, priority, due date, estimate, cycle, Linear project, labels, and new comments) show at once and reach Linear in the background, as you (your token). Descriptions stay read-only, with **Edit in Linear**.

- **One write path.** Every change to a Source Item's synced fields is an Item store action (`edit-fields`, or an undo), recorded in the activity log as yours and queued for the Source in the same transaction (`outgoing_changes` in `commander.db`), field by field and with the time you made it. Anything that changes Items through the Item store reaches Linear the same way: Todos backed by Linear issues and Ares's accepted suggestions included.
- **Sending.** The sync engine sends each Account's queued changes one issue at a time, never alongside that Account's sync, then syncs the Account again. Only changed fields are sent, labels as add/remove deltas, and comments with an id Commander made, so a retried post is never posted twice. A sync while a change is on its way keeps your value on top.
- **Offline and restarts.** Changes wait while the machine is offline or asleep, survive a restart, and go once Commander is back online.
- **Failures.** A change that can't reach Linear retries after 10, 20, 40 and 80 seconds (always waiting as long as Linear's rate limit asks); after the fifth failure, or at once if Linear refuses the change itself, the issue shows **Couldn’t sync** with **Retry**. The change stays as you made it until it gets through or you undo it. A refused sign-in shows **Reconnect** and the changes wait for it.
- **Conflicts: the newer change wins, per field.** Before sending, Commander reads the issue's history in Linear: if someone changed that field after you did, your change is dropped, Linear's value shows, and the issue says "Changed in Linear by Priya Patel at 14:02" (in its activity log too). Changes to different fields are always both kept.
- **Undo** (`Ctrl+Z` in the Section) restores the old value in Commander and queues it for Linear, under the same rule; undoing a comment deletes it in Linear.

The end-to-end tests check all of this against the fake Linear, which records issue history and accepts the writes. With `COMMANDER_TEST_HOOKS=1` they can also take Commander offline: `COMMANDER_TEST_OFFLINE=1` starts it offline, and a main-process hook switches it back.

### Ares's model (Z.ai)

Ares runs on GLM-5.3-Flash through Z.ai's OpenAI-compatible API, behind one model interface in `packages/models` (`complete({ tier, job, messages, schema?, stream? })`), so other providers can be added later without changing callers.

- **API key:** create a pay-as-you-go key at z.ai, paste it into **Settings → Ares** and press **Test**. The key is kept only in the keyring (through `apps/desktop/src/main/secrets.ts`); the Core asks the main process for it when it makes a call and keeps it in memory only. It is never written to the database, logs or the window.
- **Tiers:** Quick (thinking `low`) and Deep (thinking `high`), each with its own model, base URL and thinking level, plus per-job thinking overrides. Point a tier's base URL at any OpenAI-compatible server to use it instead.
- **Usage and the cap:** every call is logged in `commander.db` with its job, tier, model, tokens, latency and cost (never the prompt or reply), and **Settings → Usage** totals it. With a monthly cap set, 80% records one warning for the month; at the cap, Deep-tier calls go to the fallback model if one is set and otherwise fail as over cap, while Quick-tier calls carry on.
- **Tests never call Z.ai:** they run against a fake OpenAI-compatible server (`@commander/models/testing`).

### Search by meaning (local embeddings)

Search finds things by what they mean as well as by their words (#73, ADR 0007): `Ctrl+K` "the rate limiter thing" finds the Linear issue "Throttle bursts on /sync", and Ares's jobs look Memory up the same way. It runs entirely on this machine: nothing is sent anywhere.

- **The model:** IBM's [granite-embedding-97m-multilingual-r2](https://huggingface.co/ibm-granite/granite-embedding-97m-multilingual-r2) (Apache-2.0), as int8 ONNX from a pinned revision of onnx-community's conversion, every file checked against its pinned size and SHA-256 (`apps/core/src/meaning/model.ts`). It runs through onnxruntime-node in a worker thread beside the Core (`embed-worker.js`, built next to `core.js`), at the lowest priority, about 430 MB of memory while it is on.
- **First use:** about 20 seconds after Commander starts, the model (about 123 MB) is downloaded from Hugging Face into Commander's data folder, with progress in **Settings → Ares → Search by meaning**; an interrupted download carries on where it stopped, and a failed one is tried again later (or at once with **Try again now**). Until it is ready, search is by words alone. **Off** stops it and frees its memory (the files stay); on again picks up where it was.
- **Indexing:** once ready, every Item and memory is embedded in the background, four at a time, most recently changed first, and again whenever one is saved with new words; the backfill waits while you are searching, and the idle catch-up fills any gaps. On this machine (AMD Strix Halo) it embeds about 18 Items a second, so 1,300 Items take a little over a minute and 50,000 about 45 minutes, without stalling the Core.
- **Searching:** word results show at once; when you pause, the palette asks again with your words embedded (about 5 ms) and merges what meaning finds by reciprocal rank fusion, marking results found by meaning alone **related**. An exact identifier or title still comes first, and every filter applies to both halves. With 50,000 Items embedded a hybrid search takes about 100 ms. Only Items nearly as near as the nearest (and at most ten) are found by meaning. The Email Section's `/` search stays words only.
- **Usage:** each embedding call is logged on the Usage page (job, tokens and time, at no cost, under "This machine").
- **Tests never download the model:** unit tests and the end-to-end tests use a stand-in with deterministic vectors (`apps/core/src/meaning/fake.ts`; the end-to-end launcher sets `COMMANDER_TEST_EMBEDDINGS=fake`). The real model's checks run only with `COMMANDER_EMBEDDING_MODEL_DIR` pointing at its files (`pnpm test:perf apps/core/src/meaning`).

### What Ares may do on his own (Autonomy)

Every Ares action goes through one gate in the Core (`apps/core/src/autonomy/gate.ts`). His jobs register their actions and hand it **proposals**; it checks the **Settings → Autonomy** grid (a level per Action kind, with Section and per-action overrides) and either drops the proposal (Off), keeps it as a suggestion on its Item for you to accept (Ask), or carries it out through the Item store as Ares (Auto, or Auto when sure at 80% confidence or more). Act for you and Delete never go above Ask, whatever is saved, and Delete is Off until you turn it on. A proposal's steps must fit its kind: any delete step makes it Delete, and Organise may file an outside Item but not change it at its Source; a proposal that doesn't fit is refused. Anything suggested because of another Item always asks, and accepting it never starts a next step by itself.

**Ares's activity page** (the Ares tab, or click the Ares module in the header) lists everything he did or suggested, newest first, with his reason and what caused it. Accept or dismiss suggestions there (Organise and Tidy your Sources all at once, Act for you and Delete one at a time), and **Undo** anything he did.

The end-to-end tests can stand in for his jobs: with `COMMANDER_TEST_HOOKS=1` the main process exposes a hook, reachable only from the main process and never from the window, that registers actions and proposes.

### Ares's jobs

A job runner in the Core (`apps/core/src/agent/`) runs Ares's jobs on their triggers: a pause in your typing, a Source sync, Items arriving, the machine idle (catch-up work), or on request. Each job declares its name, tier, Action kind and action (registered with the gate at every start), its triggers, and how it gathers its input. A run makes one model call under the job's name, so it shows on the Usage page, and hands what comes back to the gate as proposals; Ares never writes to the database himself.

- **Quick jobs** make one call with no tools, and the reply must fit the job's fixed schema (zod). A reply that doesn't, even after one retry, is discarded and logged, never acted on. The material a job works on goes into the prompt as clearly delimited data, through the one prompt builder (`apps/core/src/agent/prompt.ts`; see Prompt-injection defences below).
- **The queue** runs a job triggered twice before it starts once, runs at most two jobs at once and never two runs of the same job. A failed or over-cap call is logged and runs again on the next trigger; after repeated failures automatic triggers wait (1, 2, 4… minutes, at most an hour). A missing key or the cap never adds to that wait.
- **What each job has looked at** is kept in `commander.db` (each Item with a fingerprint of how it was, and how far through the activity log it got), so nothing is sent or suggested twice, and it carries on where it left off after a restart.
- **Settings → Ares → Jobs** lists each job with how its last run went, a switch (off, it never runs) and **Run now**. A job whose action the Autonomy settings have Off doesn't run either. The Ares module in the header shows **Working** while a job runs and **Idle** otherwise.

**Suggest Todos** (Quick, thinking `low`) is the first. About 20 seconds after you stop typing in a Daily Note it looks at the Blocks you changed since its last run, and when the machine has been idle for 5 minutes it catches up on today's note. It sends each written Block that isn't a Todo yet (with the Blocks above it as context) and asks for `{"todos":[{"blockId","title","confidence"}]}`, where `blockId` is the short reference the prompt gave the Block (`B1`, `B2`…); any other reference is dropped. Each Todo is a proposal on its Block (Organise / "Suggest Todos"): at Auto when sure, a confident one is added at once (origin Ares, a made-from Link to the Block, the Block's Project filed as inherited), and the Block shows its checkbox; otherwise it waits as a card in the margin beside the Block, with **Add** and **Dismiss**. A dismissed suggestion, or an Ares Todo you undo, isn't offered again for the same Block text. In Todos an Ares Todo shows "Ares · 3 Oct", its made-from Link opens the Block, and renaming it leaves the Block's text alone (and editing the Block leaves its title alone).

**Rank the Dashboard** (Quick, thinking `low`) runs after each Source sync and about 5 seconds after Todos stop changing (yours, or a Todo Ares suggested or added). It looks at the open Todos (a Linear Todo as its issue), the Linear issues you created or have that changed in the last two days, the Teams Chats that may need you (a mention, an unanswered one-to-one Chat, or unread messages from the last two days; never a muted Chat), and Ares's pending suggested Todos, at most 200 a run, each in a data block of its own, 40 to a call, with today's date. For each it asks `{"ranking":[{"ref","band","rank","reason"}]}`: a band (Now, Today, Waiting on others, FYI, or none), a rank in it and a reason of a few words. Each entry is checked on its own: one naming an Item it wasn't given, a band that isn't one, or no reason is dropped, as is any Item he left out, and the band rules place those. The ranking is kept in `commander.db` (`dashboard_rankings`), each entry with a fingerprint of the Item as he saw it; nothing changed since his last ranking today means no call. It changes no Item, so it doesn't go through the gate: it applies at any Autonomy level above Off, and Ask works as Auto here (approving each row's position would make no sense), as the Settings grid's hint says.

The Dashboard shows his order and reasons (through `AresText`) and says "Ranked by Ares · 14:02" in its header. An Item he hasn't ranked, or that changed since, is placed by the band rules where they have a place for it. The rules rank everything, and the header says "Ranked by rules" (pointing at it says why), whenever his ranking can't be used: ranking is Off, the job is switched off, his last run failed (no key, over the cap, the model down) or his ranking is from another day. Pending suggested Todos show as suggestions where he ranked them (at the end of Today until he has), with **Add** (`a`) and **Dismiss**; Add makes the Todo through the gate. Cleared rows (`e`) are kept in `commander.db` too (`dashboard_clears`), so he leaves them out until their Item changes, and a cleared row still comes back when its band changes.

**Spot stuck Linear issues** (Quick, thinking `low`) runs after each Linear sync. A check in code (`packages/domain/src/linear-stuck.ts`) picks, among the open issues assigned to you or created by you, those that may have stalled: started and unchanged for 5 working days, in review with no change for 3 days, blocked by an issue that is still open, or overdue (the last two once a day has passed without a change; a comment counts as a change). Each goes to the model in a data block of its own, 20 to a call, with why it was picked, and it answers `{"issues":[{"ref","stuck","reason"}]}`. Those judged stuck go in the Update under For your information, merged by team ("2 of your Engineering issues look stuck"), each with Ares's one-sentence reason and opening its issue. An issue leaves its line once it changes, and isn't judged again until it changes and stalls again. Like the ranking it changes no Item and proposes nothing in Linear, so it doesn't go through the gate. Linear sync keeps each issue's blockers (`inverseRelations`) for this.

**File into Projects** (Quick, thinking `low`) files what the Rules miss. When a sync brings Items (and on the idle catch-up), it looks at the open Linear issues, Teams Chats, GitHub pull requests, issues and releases (open ones, and others changed in the last 14 days; never a review request, which follows its pull request) and calendar events (from yesterday to 30 days ahead, not declined, not Commander's own focus or busy blocks; a recurring series once, by its next instance: when he or you file one instance, the series' other instances follow it with no model call, "Like the other times of …", decided by the Calendar Section's Autonomy setting; one you unfile stays Unfiled) that are Unfiled, that no Rule matches and that have no suggestion of his waiting, at most 20 a run; an Item you or a Rule filed is never his to file, and one he filed stays as he filed it. Muted Chats are filed too (muting is about attention); excluded ones are gone. Each Item gets a call of its own (one outside Item per prompt, so filing it acts on that Item alone and follows your Autonomy settings for its Section, Linear, Teams, Calendar or GitHub), beside your active Projects and their Rules: an issue with its title, People, Source fields (workspace, team, Linear project, labels), a trimmed slice of its description and latest comments; a Chat with its name and type, the people in it with the Projects you (or a Rule) filed their other Chats under, and its last 10 messages, each trimmed, as untrusted text in its own block; an event with its title, calendar, organiser, attendees (people, not rooms) and a trimmed slice of its description, in its own outside block; a GitHub Item with what it is (`acme/titanlink-api#12`, its state), its title, repo and org, labels, milestone, author with the Projects you (or a Rule) filed their other GitHub Items under, and a trimmed slice of its body or release notes, in its own outside block (a Linear issue it finishes is a strong hint); all with their linked Items' Projects (codes only). A Chat is looked at again only when its name, type or people change, or once it grows past 3 messages and then 10, never on every new message. He answers `{"filings":[{"itemId","projectCode","confidence","reason"}]}`; a code that isn't an active Project's is dropped, and `"unfiled"` changes nothing. Each filing is a proposal (Organise / "File into Projects"): at Auto when sure, a confident one is filed at once ("Filed under TL by Ares", his reason in the activity log); otherwise the issue wears his **dashed Badge** (the suggested Project's code in a dashed outline) wherever Badges show: Linear and Teams rows, every Calendar view, the Todos backed by it, GitHub rows (and a pull request's review request, the Dashboard's row), Dashboard rows, and the suggested Project's page under **Ares suggests**. Confirm files the Item by you; another Project files it there by you; Unfiled turns him down. Rules still win: a Rule that matches later replaces his filing, and a suggestion overruled by you or a Rule is dismissed. Each of your answers (Confirm, Change, or `b` on an Item he filed) is recorded as a **confirmation** or **correction** activity entry (his suggestion, your choice, the Item), which can't be undone; the Memory ticket turns them into examples. Once 5 of them point one Source field value at one Project (5 issues from team OPS filed under TX, say) and none disagree, the Update asks "Always file Linear team OPS under TX?", for Chats "Always file Chats with Omar Haddad under TL?", for events "Always file events in calendar Titanlink Standups under TL?", and for GitHub "Always file acme/titanlink-api under TL?" (or the org, when answers across its repos agree) (no model needed: it is a count). **Make the Rule…** opens the Rule editor filled in, to go at the top of the list unless the overlap question places it, with the re-filing preview; dismissing it stops it coming back. **Emails, filed** (#141): File into Projects also looks at email: the latest message of each inbox thread from the last 30 days (a thread's Project is its latest message's), Unfiled, that no Rule matches, from Accounts whose mail Ares may read (see Gmail and the cloud below), and only while you have a Project. **Sort into Buckets** (Quick, thinking `low`, Organise / "Sort into Buckets", Auto when sure by default) sorts the mail the Bucket Rules miss (#141, decisions #16, #31). Outlook mail isn't asked about.
- **Suggest new Buckets** (Quick, thinking `low`) looks, at most once a week when the machine is idle, at the week's corrections of his sorting and his unsure sorts (below 0.5), when there are at least 3 of them (at most 12 emails, each in its own outside block, with what happened to each in Commander's own words). He may propose one Bucket you don't have, with a name and description ("Investors: updates and questions from our investors"), as an Update line with **Add Bucket…** (a dialog to edit it before adding) and Dismiss. **Block time for Todos** (Deep, thinking `high`, Tidy your Sources, Ask by default) finds time for the work. ### Memory: what Ares knows

Ares remembers (#74, ADR 0006). Memory sits behind one small interface (`apps/core/src/memory`): his learners write it through the Item store, the User changes it on **What Ares knows**, and his jobs look it up. Each memory has a kind, plain words, what it is about (a Person, a Project), its sources (the Items it came from), when it was learned, and whether it is **confirmed**.

- **Rules** you keep show as rule memories, pointing at the Rule; they are changed only in Settings → Rules.
- **Examples** come from your answers to Ares, as soon as you give them: each correction or confirmation of his filing ("Linear issue OPS-1 (team OPS) belongs to TX (Tactics), not TL (Titanlink)") or of his sorting of email ("Mail from news@acme.test belongs in Newsletters, not Receipts") and each Todo suggestion from a Daily Note you dismiss or undo ("Not a Todo: …"). They are yours, so confirmed. Answers given before Memory existed count too.
- **Facts** about People and Projects: **Learn facts** (Quick, thinking `low`, Organise) runs when the machine is idle on the Blocks you changed and the Linear issues changed since it last looked: your Blocks together in one call, each issue in a call of its own. A fact from your Blocks is confirmed; one from an issue is **unconfirmed**. Where People appear teaches him too: someone on at least 3 of the Items you or a Rule filed, most of them under one Project, "works mostly on" it (unconfirmed; his own filings never count).
- **Preferences:** add one by hand on What Ares knows.
- **Using it:** File into Projects, Sort into Buckets and Suggest Todos look up the memories about what they are working on, by its words (an FTS5 index beside search's, kept current as each memory is saved), by who and what it involves (a Person's handles, a Project) and, once search by meaning is ready, by meaning (#73: "the pager rota" for an issue about the on-call schedule), fused like search's retrievers. - **What Ares knows** (the Ares Section, opened from the Ares module in the header; Settings → Ares opens it too) lists everything by kind (Facts, Examples, Preferences, Rules), searchable, each with its sources and date: **Confirm** an unconfirmed fact, **Edit** any memory's words (which makes them yours, so confirmed), **Delete** one (never learned again), or add a preference. A fact whose source is deleted or tombstoned waits at the top **for review**, out of Ares's reach until you **Keep** or delete it. `Ctrl+K` lists matching memories as their own group, each opening What Ares knows at it.

### Prompt-injection defences

Only the User instructs Ares. Anything that arrived from a Source (issues, comments, and later email, GitHub and Teams) is data he reads but never obeys. The model can still be fooled, so Commander is built so that a fooled model can do no more than leave a Suggestion the User must accept (ADR 0004).

- **One prompt builder** (`apps/core/src/agent/prompt.ts`) makes every job's prompt. Ares's instructions go alone in the system message. The material goes in data blocks with a fresh random delimiter, each labelled `source="the User"` (the User's settings, Rules, Blocks and own Todos) or `source="outside"`, by where it came from, never by what it says (`apps/core/src/safety/trust.ts`). Outside text is normalised first: invisible characters and Unicode tag characters are removed, lookalikes folded, anything shaped like a tag defused, and every line marked as outside.
- **Nothing secret goes in.** The Core remembers every token and key it borrows from the secrets module, by SHA-256 fingerprint only. A prompt whose material holds one is refused, and nothing is sent (the job shows why). Credential-like text is replaced with `[removed]` in every block (`apps/core/src/safety/credentials.ts`): known key and token shapes (Anthropic, OpenAI, GitHub, Linear, Slack, AWS, Google, Stripe, GitLab, npm, Z.ai, JWTs), private key blocks, Authorization and bearer headers, cookies, `password: …`-style pairs, secrets in URLs, and long random-looking strings by entropy. It can't see a password written with no keyword near it, or short, word-like secrets. Attachments never go in: pasted images, inline data and remote images become words.
- **What the model writes is checked** before a job uses it. Every string loses the builder's internal wording (the GLM evaluation saw a summary echo it), images, and any URL the model wasn't shown. The cleaned reply must still fit the schema. A proposal from a run that read outside material names the outside Item behind it. Unless it acts only on that Item, it is chained: it always asks and shows its cause. The gate checks that again on its own.
- **Steering warnings.** Each outside Item is checked as it arrives (`saveFromSource`), by patterns for text aimed at Ares or at an AI (`apps/core/src/safety/steering.ts`), and every job's reply carries a `steering` flag naming outside blocks that tried, each with the passage it took as an instruction (`{"ref":"U1","quote":"…"}`). A flag counts only when that quote is found word for word in the Item's own text (`apps/core/src/safety/steering-flag.ts`): a model's hunch with nothing to show for it marks nothing, so a planning issue full of questions ("Decision 3: Do venues pay a listing fee?") isn't flagged. Either way the Item gets a **warning mark** ("This issue contains instructions aimed at Ares. He ignored them.") on its rows and detail panes, as does a Linear Todo of a marked issue. It also gets an injection-warning entry in its activity log, by Ares, which the Update shows, naming the Item and quoting what read like an instruction. There is no pop-up, and nothing else changes. **Not an instruction** in the Update clears the mark, logged as your correction; it stays clear while the Item's words do (a Chat's later messages don't bring it back), and comes back only if something new turns up.
- **Memory is background unless it is yours.** What Ares picked up from outside content and you haven't confirmed (a fact from a Linear issue, where People appear) reaches a prompt only in a block marked `source="background"`, and anything a prompt with background leads to is chained: always a suggestion, with its cause (ADR 0004's fifth amendment).
- **Text only.** Anything a model wrote is shown with `AresText` (`packages/ui`): plain text with light formatting, no images, no requests, and a URL clickable only if that exact URL is in the source Items. An Ares Todo the User has accepted is an ordinary Todo, shown as plain text.

### Ares's Updates

Ares never interrupts. (The one exception is the meeting heads-up below, which you turn on yourself and which says nothing but the meeting.) Anything he wants to tell you waits in his **queue**, and you get it only by asking: `U` (anywhere you aren't typing), **Ask for an update** in the header's Ares module or the Dashboard's side column, the tray menu's **Ask for an update**, or the palette command. Each runs the same **Update** Skill in the Core (`apps/core/src/updates/`), which first runs a light sync of every Teams Account (the same check as **Sync now**), waiting up to 2 seconds before going on with what's there (the sync carries on, and what it finds is for the next Update), and skips it when Teams was checked in the last 2 minutes, so reopening an Update is instant; the Skill registry (`packages/domain/src/skills.ts`) is what Conversations will use to give one when you ask in your own words. The header, the Dashboard and the tray only show a quiet count of what is queued.

- **What gets queued:** suggestions Ares wasn't sure about (merged into one line per action), each chained suggestion on its own line, outside Items that held instructions aimed at him, the month's 80% cost-cap warning (it expires with the month), and, once you have accepted the last 20 suggestions of one action without dismissing or undoing any, "Want me to just do them?". From Linear: issues a sync took off your list (reassigned, unassigned, cancelled, moved out of the Todo states, deleted), as one For your information line, and stuck issues (see **Spot stuck Linear issues** above). From GitHub: Ares's latest unseen GitHub summary (see **Write the GitHub summary** above). An Account that needs reconnecting is one line in Needs you now whose **Open** goes to Settings → Accounts; it clears itself once reconnected. Accepting that raises the action one Autonomy level, never past its hard limit; Ares never raises it himself. Other parts of Commander add their own lines through the queue's `enqueue`, each with a group, the Items it is about, a merge key and an optional expiry.
- **Every line says what, why and what to do (#186):** what it is (named: "ENG-418 “Throttle bursts on /sync” in Linear"), what happened, why it matters to you, and what to do next, or plainly "Nothing to do". Each kind of line has a plain sentence that already says all four from its Items' own data (`apps/core/src/updates/kinds/`), for example "ENG-418 “Throttle bursts on /sync” in Linear was reassigned to Priya Patel, so it’s off your Todos. Nothing to do, unless it should still be yours.", "3 of your Linear issues were reassigned, so they’re off your Todos: ENG-418, ENG-420 and OPS-12. Nothing to do, unless one should still be yours.", "Linear (Acme) needs you to sign in again, so I’ve paused syncing it and its issues may be out of date. Sign in again from Settings → Accounts." or "ENG-433 “Tidy the backlog” in Linear has a line that reads like an instruction to me: “…”. I did nothing because of it. If it’s ordinary text, choose Not an instruction."
- **Each line lists its Items:** under its sentence, each Item it is about, stamped with its Section, with a few words on where it stands ("Reassigned to Priya Patel", "In Review · unchanged for 6 days", what a suggestion would do, or the passage that read like an instruction) and its own actions: its name opens it where it lives, and as fits it **Accept** or **Dismiss** (a suggestion), **Tick** (a stuck issue's Linear Todo), **Reply** (a Chat waiting on you, opened at that message), **Not an instruction** (a warning) or **Dismiss** (off this line). A line with more than three Items folds them under **Show all**, its sentence keeping the count; a line goes once none of its Items is left.
- **The Update:** three groups (**Needs you now**, **Waiting on your decision**, **For your information**), each line one or two plain sentences with **Done**, **Dismiss** (which also dismisses the suggestions it is about), **Snooze** (later today, or tomorrow at 9:00) and **Open**, and suggestions accepted in place (several Organise suggestions at once; Act for you never in bulk). `Esc` closes it and anything untouched stays queued. After more than 8 hours with no activity Ares leads with the 5 most important things and folds the rest ("and 23 smaller things", by Section); after a busy day nothing is folded.
- **Ares's words:** "Put Updates together" is a Deep job at high thinking, made through the prompt builder like every job: each line's facts in a data block of Commander's own words, each of its Items (title, Source, where it stands, dates, people) in a block of its own, outside ones marked as outside, and the prompt's guidance for each kind of line present, with a good and a bad example. His reply is checked the same way and shown with `AresText`, and every line he writes is checked against what he was handed (`apps/core/src/updates/grounding.ts`): a name, number, date or quoted title he wasn't given, or a line that doesn't say what it is about, and that line keeps its plain sentence. What read like an instruction is shown to you but never handed back to him, and the GitHub summary's line stays in Commander's words (what's on fire is Commander's to say). The model only chooses the words; what accepting or dismissing a line does stays with the queue. Without a key, over the cap or when the model fails, the plain sentences are used, so an Update always works. It is put together in the background when you come back to the machine, so it is ready when you ask.
- **History:** every Update is kept in `commander.db`. **Past Updates** in the panel reopens the last one or any earlier one, showing what has since become of each line. Asking again with nothing new gives the same Update rather than another copy.
- **Here or away:** the main process reports `powerMonitor`'s idle time and lock state to the Core every 15 seconds and on lock, unlock, sleep and wake. Active means unlocked with input in the last 5 minutes. It drives only "You're here / Away" in the Ares module, having the Update ready on your return, the Agent's idle catch-up, and holding back the meeting heads-up while the screen is locked; it never draws your attention.

The end-to-end tests' input never reaches the system, so they stand in for `powerMonitor` with `COMMANDER_TEST_PRESENCE=here`, and with `COMMANDER_TEST_HOOKS=1` the main process exposes the tray menu to them, and notes meeting heads-ups (showing none on the desktop) for them to read and click.

**GitHub open work (#116).** The GitHub Section opens on **Your work**, beside Pull requests and Issues: **Your pull requests** (with their checks, review decision, who each is waiting on and its age), **Review requests** (those asked of you directly first, then your teams', with the team named) and **Assigned issues**, with the same rows, keys and detail pane. When the review is given or withdrawn, the pull request closes, or the issue closes or goes to someone else, the Todo goes, with an activity entry by GitHub saying why ("Review submitted", "Reassigned to priya"). **Send to Linear.** Any Todo or Daily Note Block can become a Linear issue: `l` on the selected Todo (or **Send to Linear** in its detail pane), **Send to Linear…** in a Block's margin menu (the `⋯` at the end of its row) or `Ctrl+Shift+L` in the Block, and **New Linear issue** (`c`, or the button) in the Linear Section; each is in the palette too (**Send Todo to Linear**, **Send Block to Linear**, **New Linear issue**). The issue takes the item's Project, filed as inherited. A Todo sent becomes backed by the issue (its origin shows **Linear · ENG-512**, and ticking it completes the issue); if the issue isn't one of your Linear Todos (assigned to someone else, say) the Todo goes, saying why. A Block sent gets a made-from Link from the issue, and shows the issue as a chip (identifier and state) that opens it in the Linear Section; if the Block was a Todo, that Todo becomes backed by the issue. **Undo** (the toast's, or `Ctrl+Z` in Todos and Linear) deletes the issue in Linear and puts the Todo or Block back as it was.

Every Todo belongs to a Project or is Unfiled, and shows it with its Badge (the Project's two-letter code on its accent colour, or a faint `—`). - **Name, code and accent:** rename and recode it (codes stay unique; a taken one is refused), and pick an accent from the palette of 8 or any colour. Chips go into today's note only, never into past days, and never twice for the same event: Commander remembers each event's chip (`meeting_chips` in `commander.db`), so re-opening, restarting and re-syncing add nothing, and a chip you delete stays deleted. The Core keeps every Block's Project on its Item (filed as inherited when it comes from above), so the Project filter and queries see it. **Reading email.** Email HTML is written by whoever sent it, so it never reaches the window:

- The Core sanitises each message (DOMPurify on jsdom, with an allowlist narrowed for email, and CSS rebuilt from what is allowed with css-tree): no scripts, event handlers, frames, objects, forms, media, `<meta>`, `<base>`, `<link>`, SVG or MathML; links only to web and mail addresses; remote images in `src`, `background` and CSS `url()` rewritten to Commander's image handler (or held back with no URL at all); `cid:` images to the message's own parts; everything else that names something to load, dropped. Sanitising runs in a worker thread beside the Core, each message within 10 seconds; HTML nested deeper than 3,000 elements, or too slow to sanitise, is read as text instead.
- The main process serves the result from its own protocol, `commander-mail://`, under a random token per opened message, with a response CSP of `default-src 'none'; style-src 'unsafe-inline'; img-src commander-mail:` and `sandbox`, into an iframe sandboxed with `allow-popups allow-popups-to-escape-sandbox` only: no scripts, no same-origin, no forms, no navigation. The window's own CSP is unchanged (the scheme is registered with `bypassCSP`; the session's request guard takes CSP's place for it: a document only as a frame of the window, its images and parts only as images).
- The window's session cancels every web request (only `pnpm dev`'s server gets through), so nothing in the window or a frame ever reaches the network itself. A frame showing an email never navigates: its links open in your browser through the same check as every link (web and mail only).
- Remote images are fetched by the main process, when the message's rule allows: never from this machine or the local network, no cookies or referrer, images only (up to 5 MB each, 6 at a time). Once a message's images are shown, all of them are fetched at once, so CSS that loads an image on hover or at some width tells the sender nothing more. **Gmail Accounts** show them by default, as Gmail does; **Settings → Email → Ask before showing images** holds them back, since Commander, unlike Gmail, has no image proxy, so senders may see when you opened an email and your approximate location. **Outlook Accounts** hold them back unless you trust the sender. Held-back images show as quiet placeholders, with **Show images** (this message) and **Always show from this sender** (kept per Account; Settings → Email lists them, each removable).
- Each frame is sized to its content: the main process lays the same document out once more out of sight, with JavaScript off, and reads its height.

The tab counts the reviews waiting on you. `j`/`k` move, `Enter` opens one in the detail pane and `Esc` closes it, `b` files it under a Project (recorded as yours) and `Ctrl+Z` undoes that; all are in `?`. The detail pane has **Open in GitHub**, the repo, author, state, branches, labels, assignees, the reviewers with their latest review, the change size, the issues a pull request closes (opening here when Commander holds them, else on GitHub), the body read-only as Markdown (raw HTML stays text, images become links to them and are never fetched, and only web and mail addresses open, in your browser), its Links both ways and its activity log. Comment threads aren't synced (they're expensive): opening one fetches its comments, reviews and review comments (the latest 50 of each, oldest first) and a pull request's checks (each opening its page) with one GraphQL query, under a thin "Loading discussion…" line (or what went wrong). Commander keeps them beside the Item until it next changes on GitHub, so opening it again costs nothing; after a sync brings a change, it is fetched again. Opening the Section asks every GitHub Account to sync, and its status line says when it last synced, or the error. GitHub stays read-only.

Teams shows your Teams Chats, those with an unread message that mentions you first, then other unread Chats, then the rest, each by its latest message. Each row shows the Chat's name, its type (`1:1`, `GRP`, `MTG`), its latest message as one line with its sender, the time, the unread count, `@` when an unread message mentions you, **Muted**, the warning mark if it tried to steer Ares, and its Badge. Under the Project filter, the Chat-type tabs and **Unread only** narrow the list together, each with its count. `j`/`k` move, `Enter` opens the Chat view and `Esc` goes back to the list; `b` files the Chat under a Project (`Ctrl+Z` undoes). The Chat view shows the messages by day, newest at the bottom, with senders, reactions summed ("Like 3"), **Edited** and **Deleted** marks, mentions of you highlighted and files as links; a side panel holds its Project, Links both ways and activity log. Message text is shown as plain text only (never as HTML): web and mail addresses become links that open in your browser, and no image is ever loaded (an inline image shows as "[image]" with **Open in Teams**). The Chat's menu **mutes** it (it stays and syncs, but leaves unread ordering and counts, and never reaches the Dashboard or Ares's ranking; undoable) or, after a confirmation, **excludes** it (Commander deletes its copy, leaving Links from notes and Todos showing it as gone, and stops syncing it). Settings → Teams lists muted and excluded Chats, with **Unmute** and **Include again**, which brings an excluded Chat back with an immediate check. Mute and exclude are Commander settings only: nothing changes in Teams. Opening the Section checks every Teams Account at once, and a status line says when ("Checked 14:02") or what went wrong. The Teams tab counts the unread, unmuted Chats. Replying comes next; for now the Chat view is read-only.

Once an Account syncs Channel posts, a **Channels** group follows the Chats: by team, then channel, each channel's posts by latest activity, each row with its Badge, title, who wrote last, the reply count, **New** while something from others in it is unseen and `@` while that mentions you. Clicking one opens the post view: where it was posted, the post and its replies (shown as plain text, as Chats are), a reply box that posts to the post's replies through the outgoing queue (with the same duplicate check as Chat replies, so a retry never posts twice), and its Project, Links and activity log; `b` files it and `Esc` goes back. Until then there is no Channels group at all.

Ares reads Teams too: a Chat where he judges someone is waiting on you carries a **Waiting** mark, **Waiting on you** (beside **Unread only**, with its count) lists only those, and the Chat view shows his reason with **Not waiting** (undoable). **Summarise** in the Chat view's actions puts his summary above the messages, since you last read it, today or this week. His suggested Todos wait beside the messages they came from, a suggested reply for a Chat waiting on you waits above the reply box (**Send**, **Edit**, **Dismiss**), and **Draft** beside the reply box fills it with a draft for you to send (see **Spot what's waiting on you**, **Summarise Chat**, **Suggest Todos from Teams**, **Draft** and **Suggest Teams replies** above).

Calendar shows the events of every calendar you have on, in every connected Google and Outlook Account, together in four views, switched in the sheet header and remembered on this machine: **Day** (`d`), **Week** (`w`, Monday to Sunday), **Month** (`m`) and the **Agenda** (`l`; `a` is Ares's). `[` and `]` move back and forward by the view's span (a day, a week, a month, the Agenda's days) and `t` comes back to today; all of them are listed in `?`. Day and Week are time grids on the wall clock (a 09:00 meeting stays at 09:00 on the day the clocks change), with all-day events, and timed ones of a day or more, as bars in a strip above, overlapping events side by side, an event crossing midnight split between its days, past events hatched, free ones with a dashed edge, and a **now** line in the signal colour on today. Month shows up to three events a day, all-day ones first, then **+N more**, which opens that day. Each event shows its calendar's colour as its block and its Badge as a stamp (`—` while Unfiled). Moving to days beyond what sync keeps (30 days back, 12 months ahead) shows a quiet line pointing to Google Calendar or Outlook on the web.

**Clashes.** When events from **different Accounts** overlap and you are busy in both (not declined, not marked free; tentative and unanswered invitations count; all-day events don't), both wear the **Clash** mark in every view, and the detail pane says "Clashes with *Board prep* in your sam@contoso.test calendar". Overlaps within one Account are left alone, as Google and Outlook show those already, and one meeting you are invited to in both Accounts (the same title, start and end) is taken for itself.

**Time zones.** Times follow your machine's zone. **Settings → Calendar → Second time zone** (any IANA zone, like `America/New_York`, kept in `commander.db`) adds a second column of hours beside the Day and Week grids and "15:00 here · 09:00 New York" in the detail pane. An event set in a zone whose clocks differ from yours says so there ("Set in New York time: 09:30–10:30 there").

The **Agenda**: today first (even with nothing on it), then each day with events, its events in time order and all-day ones at the top, each with its time, calendar colour, Badge, Account (when several are connected) and where it is. Days follow your machine's time zone; the Agenda shows the next 30 days, and **Show more days** adds 30 at a time, up to a year. In every view, `j`/`k` move through the days shown in time order, a click or `Enter` opens the event in the detail pane (every field above, its guests and their answers, its description through the same safe text rendering as Linear descriptions, its Links both ways and its activity log) and `Esc` closes it; `b` files it under a Project (with undo, `Ctrl+Z`), and the Project filter narrows every view, counting the events in the days shown. The side column lists every calendar, grouped by Account when several are connected, with a switch to show or hide it in this view only (remembered on this machine). Commander builds no event editor (decision #17): **Edit in Google Calendar** opens the event, and **New event** opens Google Calendar's new-event page, in your browser as that Account (`authuser`); for an Outlook Account, **Edit in Outlook** opens the event's Outlook on the web link and **New event** Outlook on the web's compose page (`outlook.office.com/calendar/deeplink/compose` for work and school accounts, `outlook.live.com` for personal ones), hinting the Account to sign in as (`login_hint`). When the window regains focus afterwards, that Account syncs again. Opening the Section syncs every Account's calendars at once, a status line says when they last synced (or what went wrong), and the Calendar tab counts today's events still to come.

Today's meetings show up wherever you work (#128). Besides the meeting chips in today's Daily Note (see Notes), the Dashboard's side column holds **Today** and **Tomorrow** schedules and a Project page's side column its Project's schedule for the next 7 days: each row's time, calendar colour, title and Badge, opening the event in the Calendar Section (declined and cancelled events are left out). The band rules put your next meeting (one that gets a chip) in **Now** from 15 minutes before it starts ("Starts in 12 minutes") until it ends ("Started 5 minutes ago · ends 10:30"), at the top of the band; other meetings stay in the schedule, not the feed. A meeting row can't be ticked; `Enter` opens it and `e` clears it.

**Invitations** (#129): an event someone else organised that you're a guest of shows **Accept**, **Maybe** and **Decline** on its Agenda row and in its detail pane, your current answer pressed; `y`, `i` and `n` answer the selected one (listed under `?`). An instance of a recurring event answers that instance; the detail pane also offers **All events in the series**. An answer is an Item store change to the synced field `response` (`seriesResponse` for the whole series), so it shows at once, `Ctrl+Z` undoes it (sending the previous answer), and it goes to the Source through the outgoing queue like a Linear edit: Google Calendar patches only your own guest line (`attendeesOmitted`) with `sendUpdates=all`; Outlook posts `accept`, `tentativelyAccept` or `decline` with `sendResponse: true` (the series through its series master), so the organiser hears. An answer you gave in Google Calendar or Outlook after the one in Commander wins (by the event's `updated` time, or Graph's `responseStatus.time`), with "Changed in Google Calendar at 14:02"; repeated failure shows **Couldn’t sync** with **Retry**. Outlook has no way to take an answer back to "not answered", so undoing your first answer to an Outlook invitation can't reach Outlook and shows Couldn't sync instead. Invitations still waiting for your answer sit in the Dashboard's **Today** band ("Dana invited you to Pricing review, Thu 15:00") until you answer them. Ares suggests replies to the ones that double-book you (see **Suggest invitation replies**).

**Settings → Calendar → Notify me 2 minutes before a meeting** is off by default. Turned on, the Core looks every 10 seconds for a meeting that gets a chip starting within 2 minutes and, once per meeting (again if it moves), has the main process show a system notification (Electron `Notification`) with its title and time; clicking it brings Commander forward with the event open in the Calendar Section. It is the one exception to "Ares never interrupts", so it says nothing beyond the meeting itself, and it is held back while the screen is locked or you are away, when no one would see it. The setting is kept in `commander.db` (`calendar_settings`).

**Events Commander writes.** Focus blocks, busy copies and meetings with guests (#132) are the events Commander creates, through the same outgoing queue as every other write (ADR 0003): the event's Item is made at once under a placeholder id and its creation queued as `create`, so it shows straight away, waits while offline, retries and shows **Couldn’t sync** like any change, and undoing it queues `delete`. A retried create never makes a second event: Google gets an event id Commander chose (its Item id, base32hex), so a repeat answers 409; Microsoft gets a stable `transactionId`. Each carries Commander's marker (a private extended property on Google, `transactionId` and a single-value extended property on Microsoft), so sync recognises it, and the Source's answer gives the Item its real id. The Commander calendar is made on first use (`calendars.insert`, allowed by `calendar.app.created`; `POST /me/calendars` on Microsoft) and found again by name after a re-sync instead of being made twice.

**Settings → Calendar → Block time across Accounts** is off by default. Add a pair ("alex@gmail.test · Google → sam@contoso.test · Outlook") and each busy event in the first Account over the next 8 weeks gets a copy on the second Account's main calendar: private, busy, titled **Busy**, with no description, place, guests or reminders, so colleagues there see only that you're busy. The copy moves and goes with its event (and goes when the pair is switched off or removed). Commander's own holds, focus blocks and copies, are never copied (a meeting made through Commander is copied like any other), so two pairs pointing at each other never loop; a copy you delete in the other calendar isn't put back. Copies are made through the gate as Tidy your Sources / "Block time across Accounts": switching a pair on sets that action to Auto in the Settings → Autonomy grid, where you can change it (at Ask, each copy waits as a suggestion on its event).

Blocks take light Markdown, stored as typed and shown rendered (the marks show faintly while you edit a Block): `# `, `## ` or `### ` at the start makes a heading (`#LT` with no space stays text), `**bold**` or `Ctrl+B`, `*italic*` or `Ctrl+I`, `` `code` `` or `Ctrl+E`, and `[text](url)` links; a bare URL becomes a link, and pasting a URL onto selected text links it. A click on a link opens it in your browser (`Ctrl+click` while editing that Block), through the same main-process check as every link in the window: only `http(s)` and `mailto` links leave. Pasting or dropping a PNG, JPEG, GIF or WebP image (up to 20 MB) saves it to `attachments/` next to `commander.db`, named by its SHA-256, and puts it in a Block of its own: `Backspace` removes it and `Ctrl+Z` brings it back. The window loads images only through `attachment://local/<name>`, served by the main process from that folder alone. The daily snapshot copies the images it uses into `snapshots/attachments/`; an image no live Block uses is deleted once no kept snapshot uses it either (and it was pasted over a day ago).

**Settings → Notes → Markdown copy folder** keeps a read-only Markdown copy of the Daily Notes, one `YYYY-MM-DD.md` per day, for Obsidian, grep and backups; `commander.db` stays the source of truth. It is off until you choose a folder with the system folder picker (Commander's own data folder and the whole disk are refused), and it can be changed or turned off. Choosing or changing the folder writes every day with something written in it; after that the Core rewrites a day's file about 2 seconds after its Blocks or Todos change, writing beside the file and renaming it into place, and only when its text changed. Top-level heading Blocks become headings with their Blocks as a tab-indented list beneath, other Blocks become list items, Todos are `- [ ]` / `- [x]`, a Block's own Project is `#LT` (inherited ones aren't repeated), `[[` links are `[[YYYY-MM-DD]]` and `[[Project name]]`, a meeting chip (or any event link) is the meeting's line, `- 10:00–10:30 Weekly sync with Priya` (struck through with "(Cancelled)", or "(Moved to Thu 10:00)", as it stands for that day), and images are copied into `attachments/` there and embedded as `![](attachments/<file>)`. Commander writes only those files, never reads anything back, and never deletes or touches anything else in the folder, so it can sit inside an Obsidian vault; edits made to the files are overwritten on the next write, as each file's first line says. If the folder can't be written (gone, or no permission), Settings → Notes says why and Commander keeps trying every 15 seconds; editing never waits on it.

## Tray and summoning

Commander is meant to stay running. Closing the window hides it to the tray and the Core keeps working. Click the tray icon or use its menu (**Open Commander**, **Ask for an update**, **Quit Commander**) to get it back; **Quit** is the only way to stop it. On Hyprland the tray needs a StatusNotifierItem host in your bar, such as waybar's `tray` module or DankMaterialShell. Launching Commander again while it is running just brings the running window forward.

### A key to summon Commander (Hyprland)

Electron's global shortcuts don't reach Hyprland, so bind a key in Hyprland to the `commander-show` helper instead. It sends `SIGUSR1` to the running app (found through its pid file, `$XDG_RUNTIME_DIR/commander.pid`), then focuses the window with Hyprland's dispatcher. That brings Commander forward from any workspace, or back from the tray, in about 20–35 ms.

Put the helper on your `PATH` once (or use its full path in the bind):

```sh
ln -s "$PWD/apps/desktop/bin/commander-show" ~/.local/bin/commander-show
```

Lua config (`~/.config/hypr/hyprland.lua`):

```lua
hl.bind("CTRL + SHIFT + space", hl.dsp.exec_cmd("commander-show"))
```

Text config (`~/.config/hypr/hyprland.conf`):

```ini
bind = CTRL SHIFT, space, exec, commander-show
```

The helper works out which kind of config you run (from `hyprctl -j status`) and uses the matching focus dispatcher: `hl.dsp.focus({ window = "class:^(commander)$" })` on Lua, `focuswindow class:^(commander)$` on text. Commander's window class (Wayland app_id) is `commander`, if you want window rules for it. `commander-show` exits with status 1 and says so if Commander isn't running.

### Start at login

Off by default. Turning it on writes an XDG autostart entry, `~/.config/autostart/commander.desktop`, which starts Commander hidden in the tray (`--hidden`); turning it off deletes the entry. Hyprland doesn't run XDG autostart entries by itself: they run if your session starts `xdg-desktop-autostart.target` (uwsm does) or runs something like `dex -a`. Otherwise start Commander from your config's start-up commands instead (`exec-once` in a text config).
