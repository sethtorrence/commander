# Memory is found by its words and its fields, and what Ares picks up from outside stays background

Ares remembers (#74, decision #19): the User's corrections and confirmations of his filing, Todo suggestions the User dismissed or undid, facts about People and Projects picked up from Daily Notes and Linear issues (and from where People appear), the User's preferences, and the Rules. Every memory records where it came from and when, and his jobs look up the relevant ones and put them in their prompts. Memory is long-lived and central, so it sits behind one small interface (`apps/core/src/memory`, `MemoryStore`): learners `learn`, the User `change`s (confirm, edit, keep, delete, add a preference), What Ares knows `list`s, the palette `search`es and jobs `lookup`.

**Found by words and fields, not by meaning (yet).** #19 said memories would be embedded and looked up by meaning. A local embedding model conflicts with "Z.ai for everything" and "no first-run model download", so #73 is parked for the owner. Memory v1 looks memories up the way global search finds Items: an FTS5 word index over each memory's text and keywords (words it is found by but never shown, such as an example's Item's title and team), tokenised like search's, kept current in the same transaction as each save, and rebuilt from the memories when missing. Beside it, a lookup by fields: the People (by Person, or by any of their handles, widened through People so a fact learned against a Linear user is found by an email address of the same Person) and Projects a memory is about. The two are fused by reciprocal rank, as search fuses its retrievers. Each is a `MemoryRetriever` that hears every save (`put`) and delete (`drop`); search by meaning, if #73 goes ahead, is one more retriever, and no caller changes. A job's lookup asks with the meaningful words of what it is working on (any of them, ranked by bm25); the page and the palette ask with what the User typed (every word, the last as a prefix).

**Not Items.** Memories live beside the Items in their own tables, written only through the Item store, like Projects and People. Their sources are links to Items, without a foreign key: a source Commander no longer holds is shown as gone. Rule memories are not stored at all: they are the Rules, shown as memories, so they can never drift from the one list where Rules are changed. A memory learned again (the same key: the activity entry or proposal it came from, the fact's words, the Person and Project for a People-to-Project fact) gains the new sources; one the User deleted is kept as a tombstone, so it is never learned again. Learning examples follows the activity log and the gate's record from where it got to, so answers given before Memory existed count too.

**Trust (ADR 0004, its fifth amendment).** A memory is **confirmed** when it is the User's: their answers (examples), their words (facts from their Blocks, preferences, anything they edited) or a fact they confirmed. Anything else (facts from Linear issues, People-to-Project facts from where People appear) is **unconfirmed**. Confirmed memories go in a job's prompt as the User's own material; unconfirmed ones go in a block of their own marked `source="background"`, and any proposal from a prompt that held background is chained (always Ask, with its cause), so what Ares picked up from outside content can never lead to more than a Suggestion. An example names its Item by its Source facts (identifier, team, Linear project, labels; a Chat's people; an event's organiser and calendar), never by its free text, so nothing written by someone else rides into the User's block. A fact whose source is deleted or tombstoned is **for review**: shown at the top of What Ares knows and left out of every lookup until the User keeps or deletes it. A People-to-Project fact never acts as a Rule: Rules and the User's filing never reach Ares at all, and the jobs' instructions say such a fact never outweighs the Item's own facts.

We chose this over waiting for embeddings because the email work that needs Memory (#141, #143) shouldn't wait on a model decision, and words plus fields already find what the filing and Todo jobs need: a similar Item shares its team, labels, people and words. The cost is that a memory phrased differently from the Item it should help ("the pager rota" vs "on-call schedule") isn't found until search by meaning arrives; and that unconfirmed facts only ever produce Suggestions until the User confirms them.

**Amendment (#73): and by meaning.** The owner approved a local embedding model, so search by meaning arrived as the third `MemoryRetriever`, as planned here: memories are embedded in the background beside the Items, and a job's lookup brings the embedding of what it is working on, so "the pager rota" is found for "the on-call schedule". The word index and the lookup by fields are unchanged, and so is trust. See ADR 0007.

**Amendment (#194): a memory's source can be a Conversation turn.** What the User tells Ares in a Conversation is kept with their turn as its source, not an Item: `memory_turns` beside `memory_sources`, again with no foreign key, so a Conversation deleted leaves its memories, shown as from "a deleted Conversation". A fact the User told Ares never goes for review when an Item source goes, because they said it. Each row also keeps what the turn did and what the memory was before, so the line under Ares's answer can Undo it, which is why a memory the turn made is removed outright rather than kept as a tombstone. Saying something again in a Conversation keeps it again even after the User deleted it: the tombstone stops Ares relearning it from a Block or an issue, never the User's own words. Told facts and preferences use the same key as Learn facts (their words), so the same fact from a Daily Note and a Conversation is one memory with both sources. Trust is unchanged: the User's words are confirmed, and nothing from an Item there ever becomes so (ADR 0004's seventeenth amendment).
