# Search and Memory find by meaning too, with an embedding model on the User's machine

Search should find things by what they mean, not only by the words in them: "the rate limiter thing" should find the Linear issue "Throttle bursts on /sync" (#73, decisions #29, #19, #6). ADR 0006 left this parked, because a local model conflicted with "Z.ai for everything" and "no first-run model download". The owner has since approved a local embedding model: Z.ai's API has no embeddings endpoint, and nothing the User keeps should leave the machine just to be searchable.

**The model runs in the Core, off its main thread.** IBM's granite-embedding-97m-multilingual-r2 (Apache-2.0), int8 ONNX, through onnxruntime-node in a worker thread at the lowest priority. It is the small model of the Granite R2 pair #6 named (the 311M one is about three times the size and cost per Item for a few points of retrieval quality), multilingual (Tagalog is among its best-supported languages), and 384-dimensional. Its files come from a pinned Hugging Face revision, each checked against a pinned SHA-256, downloaded once into Commander's data folder on first use with progress in Settings → Ares, resumably. Settings → Ares can turn it off. Every call goes through the model interface's `embed(texts)`, so a hosted embedding model could replace it, and is logged on the Usage page.

**Plain search never waits for it.** The word index stays exactly as it was: written in the same transaction as each change, answering at once. The embeddings can't be written that way (the model is asynchronous and slow by comparison), so the Item store marks an Item's embedding missing or out of date as it writes, and the Core's meaning side embeds what is waiting in the background and saves it back through the Item store, still the only writer. A changed Item keeps its old embedding (and is found by it) until the new one is saved; a tombstone's goes at once. The palette shows word results first and asks again, once the User pauses, with their words embedded; the two lists are fused by reciprocal rank, exact identifiers and titles stay first, and every filter applies to both. Until the model is ready, or with it off, search is words alone.

**Vectors live in ordinary tables, compared with sqlite-vec.** Each embedding is a float32 BLOB beside the word index (`search_vectors`, `memory_vectors`), derived data outside the Drizzle schema like the word index, and found by an exact scan with sqlite-vec's `vec_distance_cosine` (a pinned 0.1.9) joined with the tables the filters live in. At Commander's scale this answers in about 100 ms for 50,000 Items and a few milliseconds for the owner's 1,300, with filters exact. We didn't use sqlite-vec's `vec0` tables: its KNN is also a scan, its filtering would need every filter copied into it, and its fast indexes are alpha. If sqlite-vec can't load, the same function runs in JavaScript. An embedding model's similarities crowd together, so a result is found by meaning only if it is nearly as near as the nearest and above a floor, at most ten.

**Memory is found by meaning too.** The embeddings retriever ADR 0006 left a seam for is now Memory's third retriever. Ares's jobs (File into Projects, Suggest Todos) embed what they are working on before building their prompt and look memories up by words, fields and meaning together. Nothing about trust changes: a memory found by meaning is confirmed or background exactly as one found by words (ADR 0004's fifth amendment).

We chose this over staying with words alone because the gap ADR 0006 named ("the pager rota" vs "on-call schedule") is exactly what Memory and search keep missing, and over a hosted embedding API because it would send everything Commander holds to a third party. The costs: a one-time 123 MB download from Hugging Face, about 430 MB of memory while it is on, and a background backfill (about 18 Items a second on the owner's machine: a minute for 1,300 Items, most of an hour for 50,000) during which search by meaning is incomplete.
