# Two-way sync writes go through the Item store, field by field

A change made in Commander to a Source Item (a Linear issue's priority, a new comment) is an ordinary Item store action, and the Item store queues it for the Source in the same transaction: one row per **synced field** (`priority`, `label:<id>`, `comment:<id>`), with the time the change was made. The sync engine only sends what is queued. So the User's edits, undo, a Todo ticking through to the Linear issue behind it, and Ares's accepted suggestions all reach the Source by one path, with no caller needing to remember to "also sync it", and a crash can never keep the change while losing its write-back.

Working field by field is what makes this safe. An edit names only the fields it changes (`edit-fields`), so it can't carry a stale copy of the rest of the Item; undo restores only the fields its entry changed, so a comment someone added in Linear meanwhile is never deleted by undoing your priority change; a sync keeps queued values on top; and the conflict rule ("the newer change wins, per field", from the Source's history) compares like with like. The queue keeps each field's last-synced value, so a field changed back to what the Source has drops out and only changed fields are sent.

**Amendment (#142): Bucket labels.** An email's mirrored Bucket is a synced field like any other (`bucket-mirror`, the Bucket its Commander label or category names), set by the Item store only for an Account that mirrors its Buckets and queued with the change that moved the email. What doesn't fit one Item, the labels themselves (made, renamed with their Bucket, deleted with it or on request), is kept as desired state in the Item store (`bucket_mirror_labels`: each Bucket's label as last asked for) and carried out by the sync engine as a plan, on the Account's queue before its writes, so they find the labels they name. A plan is idempotent (a label already there or already gone is fine), survives restarts because the state it comes from does, and holds the Account's writes back while it fails rather than letting them make labels of their own. Commander only ever renames or deletes labels named as its own (`Commander/…`, `Commander: …`).

We chose this over a separate write API beside the Item store, which would have let changes bypass the queue (or the queue bypass the activity log), and over sending whole Items, which Linear can't merge (it has no version check, and descriptions are replaced whole). The cost: the Item store knows which detail fields sync (the domain's `synced-fields.ts`), and an `update` that rewrites a Source Item's whole detail is still queued field by field, so callers should prefer `edit-fields`.

**Amendment (#138): messages written in Commander.** A message the User writes is not a field of anything: it goes whole. It takes this path all the same. Its first save makes its `email` Item (under a placeholder external id, as an event Commander makes does) and queues the change `draft`, the whole message as the Source should save it in Drafts, in the same transaction; later saves fold into the one waiting. Send queues `send`, held in the queue until the end of the Undo time (`holdUntil`, the row's next attempt), so Undo is taking the row out while it is still only pending, never once it is on its way; and discarding queues `delete`. These are not synced fields: `edit-fields` can't make them, a sync never folds them away, and only the User sends (the Item store refuses a send from anyone else). Sending can't be taken back once it has reached the Source and the Source takes no idempotency key, so it leans on the queue's `attemptedAt`: an attempt whose outcome is unknown is retried only after the adapter looks for what it did, by Commander's id on the message (a header in Gmail, an extended property in Outlook), and when it can't tell it sends nothing and stops with Retry. The Source's answer names the Item (`commanderItemId`), and a sync that gets there first is matched by the message's Message-ID, so the sent message is one Item, once in its thread.

**Amendment (#139): send later.** A scheduled message takes the same path; its Account decides who holds it until its time. One Commander sends (Gmail, and personal Outlook.com until Microsoft's hold is tested there) waits in its record, a draft saved to the Source's Drafts, and not in the queue: the Core's send-later clock queues its `send` at its time, with no Undo hold, and only while Commander runs and the machine is awake. So the queue never holds a message that must not go late, and nothing the sync engine does at start-up or on waking can send one by surprise: a start or a wake that finds its time passed marks it missed, for the User to decide in the next Update; offline at its time, its `send` is queued and waits like any other. One Microsoft holds (an Outlook work Account, told apart by its tenant) is queued as `send` at once, carrying its time (`deferUntil`), which the adapter writes as Outlook's deferred-send property, so Exchange keeps it in its Outbox and sends it with Commander closed. Taking it back is the change `cancel-send` (Commander's id finds it in the Outbox), queued ahead of what follows on the same Item (its draft again, or a `send` at another time); the Item goes back under its placeholder id, so the never-twice rule (a draft gone since an attempt counts as sent) can't mistake a message taken out of the Outbox for one that went, and a cancel that finds it already in Sent Items hands back the sent message, so nothing goes again. Neither is a synced field; only the User schedules, and the gate refuses a proposal naming `cancel-send` as it does `draft` and `send`.
